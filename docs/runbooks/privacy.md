# プライバシーと退会の運営

この手順は `docs/development.md` の「プライバシー・規約・退会の実装計画」の「公開前・運営・障害復元の手順」から移しました（TB-150、2026-11-18）。1、2、4 は公開前に行った確認で、設定を変えたときにやり直します。

1. 開発環境で `0014_privacy.sql` とコードを適用し、旧access tokenの変換完了、毎時処理、D1・DO・R2の削除・解除失敗の再試行を確認します。未完了ジョブの件数・最終試行時刻を運営者が調べ、内容・メール・トークンをログやIssueに転記しません。
2. Google／Discordの実OAuthで同じ本人・取消・別人・期限切れ・在室拒否・全端末失効・新規再登録を確認します。scopeとURLをコンソール設定に合わせます。Googleのホームページは `https://tetraboard.net/`（総合ロビーの公開で変更。[仕様](../specs/privacy.md#文書同意問い合わせ)）、ポリシーは `https://tetraboard.net/privacy`、規約は `https://tetraboard.net/terms` とし、所有ドメインを確認します。開発と本番のOAuthプロジェクトの分離も確認します。
3. 運営者が `support@tetraboard.net` の受信・返信と窓口の継続管理を確認します。削除依頼は対象URL・本人の事情を確認し、同名ゲストだけで本人と断定しません。本文や転載の個人情報を個別に確認し、処理内容と必要な証拠保持期限を本人へ案内します。残す開発課題は個人情報を除いてIssueへ移します。
4. CloudflareのD1復元可能期間、R2とログの保存・閲覧権限・処理先・保存期間を実設定で確認し、公開文書へ必要な具体値を反映します。自動テストのローカルR2削除を提供者のバックアップ消去と扱いません。
5. 障害復元では先に受付後の削除台帳と未完了ジョブ、画像の削除先索引を保護された保存先へ確保し、通信受付を停止します。D1／DOを復元しても公開を再開する前に新しいコードとマイグレーションを適用し、確保した削除済み識別子・旧部屋世代の対応を戻します。復元した本人の情報へ削除処理を再適用します。退会の台帳（`deleted_accounts`）の行は `completed_at_ms` を NULL（未完了）にして入れ直してください。毎時の退会の処理が、未完了の退会について受付のときと同じ伏せ字と削除をやり直します（D1 のトリガーは TB-155 で消したので、行を入れ直すだけでは伏せ字になりません）。そのうえで、棋譜・索引・DO・R2・認証が戻っていないことを検証してから再開します。削除台帳まで古い時点へ巻き戻して公開しません。

実OAuth・メール受信・提供者バックアップ／ログ設定・実機の文章と操作の確認は自動テストでは保証せず、確認したときは記録を残します。
