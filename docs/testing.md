## CIの実行範囲

CIの入口は `.github/workflows/ci.yml` です。設計判断は [ADR 0007](adr/0007-ci-and-tests.md) にあります。

- `checks` ジョブは、PRとmain・developへのpushのたびに、`packages/ai` を除く全workspaceのformat・lint・型・全テスト、環境分離の検査、本番と開発のWeb・Adminビルド、Workerのdry-runを実行します。
- `ai` ジョブは、AIのパス（ワークフローの `Detect AI changes` に列挙）に差分があるときと、mainへのpushのときだけ走ります。`bun run check:ai`（Rustのfmt・clippy・testとAIサービスの統合テスト）、本番AIのコンテナ4つのビルドと起動確認、開発AIのdry-runを行います。開発AIのdry-runもDockerイメージをビルドするため、`checks` では行いません。mainへのpushでは本番AIのdry-runも行います。
- `ai` がskipされたら、AIの検査は実行されていません。skipを成功とみなしません。AIのテストやスクリプトが新しいファイルを読むようにしたら、同じ変更でAIのパスの一覧に足してください。
- `deploy` ジョブは、main・developへのpushで `checks` が成功し、`ai` が成功またはskipのときに走ります。本番AIのデプロイは、AIのパスに差分があるときだけ行います。
- 差分の基準は、PRではPRのベース、pushではpush前のコミットです。マージ後のpushでも `checks` を再実行し、PRの成果物をデプロイへ流用しません。PR更新時には同じPRの古い検証を取り消します。

ローカルの `bun run check` も `packages/ai` を含みません。AIに触れる変更では `bun run check:ai` も実行してください。

非公開リポジトリの現行プランではブランチ保護を強制できないため、GitHub CIの成功と開発者のマージ承認を運用で維持します。

### 環境分離と資産の受け渡し

個人設定なし・競合する.env・競合する.dev.varsの実Worker検証と型生成の一致を毎回確認します。この3状態には異なるローダー分岐があるため、起動コストを理由に省略しません。

型チェックが成功したCI内では `build:assets` で同じVite・公開ロビー生成・chunk／WASM検査を実行します。手元の `bun run build` は型チェックを含みます。本番と開発でcanonical・robots等が異なるWeb資産は別々に生成します。

本番は本番build直後に `web-production-<SHA>`、開発は開発build直後に `web-development-<SHA>` をuploadします。deployは同じSHAのartifactをdownloadします。既存のmigration前後のbranch最新性チェック、デプロイの直列化、公開後検証を維持します。

### 実行の分割とテスト品質

`bun run check` は `packages/ai` を除く全体検証です。テスト実行の並列数はCPU数と4の小さいほうです。Workerのテストは、Vitest標準の `--shard=1/2` と `--shard=2/2` で2つの独立したVitest／Miniflareに分けて動かします。新規ファイルも必ずどちらか1群へ入ります。純粋関数とDOMのworkspaceも空いた枠で実行します。2026-11-14にファイルサイズで均等化する自作の分割と比べ、遅いほうの群の時間が同等（0.98倍）だったため、自作の分割をやめました。Bun内蔵型チェックはCPUを内部並列利用するためworkspace間では直列です。

各Workerプロセス内の `--max-workers=1 --no-isolate` は維持します。[CloudflareのWebSocketとストレージ分離の制約](https://developers.cloudflare.com/workers/testing/vitest-integration/known-issues/#websockets)に対応するためです。共有永続ディレクトリは指定せず、各プロセスが独立したD1・DO・R2とmodule cacheを使います。Vitestの結果キャッシュは無効にし、並列プロセス間のresults.json書込み競合と過去の時間による実行順変更を避けます。各群内は明示的にファイルサイズ降順・同サイズはパス順で実行します。`bun scripts/ci/verifyWorkerIsolation.ts` は同じD1主キー・DO ID・R2キーへ異なる値を同時保存し、両方の書込み後に自分の値だけを読めることをbarrier付きで確認します。新しい並列化やCloudflare plugin更新時に実行してください。

Workerの全テストを分割して実行し、認証・認可・アカウント分離・合法手・CPU・再接続・DO復旧・D1保存／migration・大会の競合を維持します。CI高速化のためにケースを削除・skipしたり、timeoutを延長したりしません。複数ゲームの同じシナリオは、dispatch・認可・保存の接続ミスを検知するため保持します。時間プリセットの網羅はAPI層と純粋時計層で一部重複しますが、CIでAPI42件が約0.4秒のため削減対象にしません。公開CPUの合法手・決定性・入力不変と棋力fixtureも、実行コストに見合う回帰価値があるため維持します。

単体で代替可能な時計・期限の純粋関数はWorker内に残します。現状の実行コストは小さく、移管に伴う境界の変更を今回追加する効果が小さいためです。終了済みファイルの全DO Alarmを列挙して停止する案は、片付けコスト増加と終了待ちが発生したため採用しません。

並列実行の失敗は子プロセスの終了コードで伝播し、開始済みの検証を回収してから失敗にします。失敗を成功へ変換しません。未発見のテスト間状態依存や、将来の群ごとの時間の偏りは残るリスクです。`bun run test:serial`（分割なし・並列数1）と通常分割で切り分けてください。

### 型チェックの方式と範囲

通常の `bun run typecheck` とCIのcheckはBun内蔵チェッカーを使います。ルートから全workspaceの `typecheck` を順次呼び、Webの5設定・Workerの3設定と、ほかの9workspaceの各設定を検査します。Web・Workerの `tsconfig.check.json` は参照をまとめるためだけの設定で、各対象のコンパイラオプションを維持します。protocolのBun型定義は明示します。Workerの型生成は従来どおり固定した設定例から先に行います。Web・Adminのビルド前の型検査も内蔵チェックです。

`bun check` という名前だけでは既存のcheckスクリプトと区別できないため、内蔵チェッカーの呼出しには常に `--no-script` を付けます。miseより古いBunは共有スクリプトで拒否し、旧Bunでの再帰実行を防ぎます。`bun run typecheck:tsc` は従来のTypeScriptによる比較用で、通常CIには重複して加えません。エディタとCIの診断差はこのコマンドでも確認します。Bun更新時には型検査専用fixture、未使用の `@ts-expect-error`、全対象のエラー検出、固定設定からの型生成と必須5コマンドを再確認します。

測定コマンドは `mise exec -- bun run typecheck`、`mise exec -- bun run --bun typecheck` と、`mise exec -- bun run --cwd apps/worker cf-typegen` に続く `mise exec -- bun check --no-script --all -b <一時参照設定>` です。一時参照設定は `files: []` と `references` で既存17対象を列挙しました。対象はWebのapp・node・test・type-tests・buildの5設定、Workerの本体・test・scriptsの3設定、Admin・AIと7パッケージの各設定です。参照する設定ごとの `include` とコンパイラオプションを維持し、Webの型検査専用fixtureやビルド用コードを省略していません。

互換性には次の差があります。

- このリポジトリの `bun check` は既存の `check` スクリプトを実行します。内蔵チェッカーには `--no-script` が必要です。さらにルートにtsconfigがないため、無引数の内蔵チェックも停止します。`bun check .` は各ファイルの最寄り設定を使うため、複数のtsconfigで同じファイルを検査する現行方式と同一視しません。
- Bun 1.4.4の `-b` は一度に一つの参照元設定を受け付けます。複数の設定ファイルを直接渡して検査前に停止した結果は、上の測定から除外しています。
- 測定時のprotocol設定は暗黙に読み込まれるBunの型定義に依存していました。内蔵チェッカーでは `URL`・`TextEncoder`・`crypto`・`bun:test` が見つからず10エラーになりました。protocolだけに `types: ["bun"]` を明示する一時的な継承設定では全17対象・1,951ファイルが成功しました。この一時設定は測定後に削除し、採用時は正本のtsconfigへ明示しています。
- 意図的な `string` への数値代入（TS2322）と、未使用の `@ts-expect-error`（TS2578）を17対象すべてに一時追加しました。各対象を個別に起動したNode版tsc・Bun版tscと、参照設定を使った内蔵チェックの3方式すべてが、全17対象で両方を検出しました。確認後に元ファイルをバイト単位で復元し、一時ソースを削除しました。既存スクリプトは最初の失敗で後続のtscを実行しないため、検査範囲の確認には個別起動を使っています。
- 内蔵チェッカーはインストール済みTypeScriptとは別の版・標準ライブラリを持ち、宣言ファイルや `.tsbuildinfo` の出力も行いません。この比較と既存の否定fixtureの成功は、すべてのTypeScriptコードに対する100%互換の証明ではありません。

内蔵チェッカーの契約と意図的な差は[Bunの公式文書](https://bun.sh/docs/runtime/check#differences-from-tsc)、1.4.4の変更は[リリース記事](https://bun.sh/blog/bun-v1.4.4)を参照してください。この比較後に開発者の採用指示を受け、上記の方式へ移行しています。全体を一つにまとめた測定用設定は採用せず、workspaceの自動検出と各workspaceでの部分実行を維持しています。
