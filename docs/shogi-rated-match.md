# 将棋のレート戦

2026-11-09に開発者が承認した通常将棋（`shogi`）のレート戦の仕様です。将棋ロビーのダイアログから検索を開始し、対局・終局結果の確認・再参加まで行えます。

## 参加と認定

- 登録アカウントが専用の待機列から参加できます。持ち時間は1人5分＋30秒の秒読みに固定し、先後・着手・終局は[通常将棋のルール](rules/shogi.md)に従います。
- 初期レートは1500です。最初の有効な5局を認定戦とし、対人戦と補充CPU戦の両方を数えます。5局目の結果を反映した後にレートを公開します。CPU戦だけで認定を終えた人には、初めての有効な対人戦を終えるまで「対人戦未経験」と表示します。
- 専用マッチングから開始し、終局結果が保存された対局を対象にします。開始後の投了・退室・時間切れ・通信切れの復帰期限切れは通常将棋の裁定どおり敗戦です。開始前の取消や入室失敗、AI障害で代替手を使った局は、認定局数とレート更新の対象外です。
- レートは専用マッチングの対局で更新します。通常ルームと「CPUと遊ぶ」の記録、および既存の勝利数・対局数ランキングは[通常将棋の集計仕様](../README.md#通常将棋)に従います。

## 対戦相手の選定

最も長く待っている人を起点に、人間の相手を優先します。待機時間によって許容するレート差を広げます。

| 起点の待機時間     | 許容するレート差 |
| ------------------ | ---------------: |
| 0秒以上・5秒未満   |          100以内 |
| 5秒以上・10秒未満  |          200以内 |
| 10秒以上・15秒未満 |          300以内 |

15秒の時点で条件内の人がいなければ、採用済みの基準レートが本人に最も近いCPUの補充を試みます。枠が埋まっている場合は元の待機順で再試行し、対人戦の成立と取消を受け付けます。ダイアログの待機人数には、そのゲームで待つ人間と、補充時刻を過ぎて枠の空きを待つ組合せの不足CPU席を含めます。CPUであることとレートへの反映は対局前に表示します。入室と開始カウントダウンは成立後に行います。

待機の継続と復元、別タブからの明示引き継ぎ、通常席・大会待機との同時参加防止、接続確認後の自動開始には、[四人リバーシのランダムマッチ](matchmaking.md)の仕組みを利用する方針です。

将棋は `/api/matchmaking/shogi` を使用し、四人リバーシと別の待機列で組み合わせます。専用ルームは認証済みの人間全員が接続してから5秒で自動開始します。入室期限切れでは、参加を継続できる人を元の待機順で戻します。新規参加には `SHOGI_MATCHMAKING_ENABLED=true` と将棋AI Serviceの接続設定が必要です。フラグは開発環境の構成で有効、本番とローカルの既定構成で無効です。

`/games/shogi?matchmaking=1` で将棋ロビーのダイアログを開きます。旧URLの `/games/shogi/matchmaking` からも開けます。ダイアログは本人の現在のレートを大きく表示し、認定前は有効局数を表示します。「対戦相手を探す」と「戻る」は全幅で縦に並べます。マイページの将棋の戦績欄では、「対人戦のみ集計」の上にレートまたは認定進捗を表示します。終局後の「もう一度マッチング」からはダイアログを開いて検索を始めます。

検索中に閉じようとすると、検索をやめるか確認します。確認中も検索を続け、成立を検知したらすぐに入室します。取消と成立が競合した場合は、サーバーで確定済みのマッチを優先します。入室後の5秒のカウントダウンで、対人戦またはCPU戦、持ち時間、レート対象であることを表示します。

開発検証では下記の5段階の暫定基準レートを用い、同じ距離に2つのCPUがある場合は基準レートが低い方を選びます。割当時にCPU設定の版と基準レートを固定し、着手要求に対応する探索予算を渡します。

## レート更新

対人戦とCPU戦で一つのレートを使います。対局前のレート差からEloの期待得点 `E = 1 / (1 + 10^((相手のレート - 本人のレート) / 400))` を求め、`K × (実際の得点 - E)` を加えます。勝ちは1、引き分けは0.5、負けは0です。対人戦は両者をそれぞれの認定状態に応じて更新し、CPU戦は人間側を更新します。5局目には認定中のKを使います。

| 本人の状態 | 対人戦のK | CPU戦のK |
| ---------- | --------: | -------: |
| 認定中     |        64 |       48 |
| 認定後     |        32 |       16 |

認定後に同レートの相手に勝つと、対人戦では16、CPU戦では8増えます。負けた場合は同じ幅で減り、引き分けでは増減しません。終局後に認定の進捗またはレートの増減を表示します。再送や保存の再試行があっても、同じ対局の結果を一度だけ適用します。

サーバーは棋譜を検証し、対局結果と各参加者の更新前後のレート、有効局数、対人戦数を一つのトランザクションで保存します。レートの保存時に丸めは行いません。前局の結果の保存が完了してから再参加でき、次の相手の選定に更新済みのレートを使います。

結果画面では参加者の名前の右に、認定後の対局時点のレートと増減を表示します。認定中の本人には有効局数を、認定中の相手には「認定中」を表示します。CPUにはその局に割り当てた固定の基準レートを表示します。保存中は結果の確定を待ち、集計対象外なら理由を表示します。表示上のレートは整数に丸め、増減は表示した更新前後のレートの差です。認定後のレートと「対人戦未経験」は将棋の公開プレイヤープロフィールでも確認できます。

## CPUの採用前検証

オープンソースのUSIエンジンである[やねうら王](https://github.com/yaneurao/YaneuraOu)を第一候補としてサーバー側で検証します。通常将棋のGameRoomが合法手・時計・勝敗を確定します。

1. 本体の版、評価ファイル、定跡、探索設定を固定します。本体はGPLv3です。使用する評価ファイル・定跡の利用条件は個別に確認します。
2. 探索量や候補手の選び方が異なるCPU設定を作り、先後を入れ替えたCPU同士の対局で、設定間の強弱と合法手の返却を確認します。
3. CPU同士の勝ち・負け・引き分けから、CPU間のEloの差を推定します。中間の設定を1500に置き、他の設定の暫定基準値を決めます。公開前の測定はCPU同士で行います。1500は計算上の基準で、人間の1500との互角を確認した値ではありません。
4. 既存のAI Serviceのコンテナ構成で、冷起動を含む応答時間、同時対局時の遅延・失敗率、メモリ使用量を測ります。

基準レートはエンジンと設定の版ごとに固定します。公開後はレート戦の結果を使い、期待得点と実際の成績の差や、CPU戦が多い人のレート変動に偏りがないかを確認します。ずれが続く設定は基準レートを見直します。

エンジンの採用、CPUの段階数・基準レート、採用済みCPUを割り当てられない場合の挙動は、検証結果をもとに決定します。

### 開発環境での接続

開発環境の通常将棋Lv2を検証に使います。WorkerとAI Serviceの両方で `AI_SHOGI_ENABLED=true` を設定し、既存の認証を通して `POST /v1/shogi/move` に着手履歴を送ります。AI Serviceは前述のMaterial版を1プロセスで起動し、同時に受け付けた最大4件を順番に処理します。検証対局の予算は256ノードで、Service側の応答期限は待ち時間と起動を含め4秒です。タイムアウトした探索プロセスは終了させ、次の要求で起動し直します。

複数の将棋対局で使う専用コンテナは、最後の要求の完了から11分間アイドル状態が続くと停止します。通常対局で選べる最大の持ち時間10分＋秒読み30秒と、次のCPU要求までの待ち時間を含む設定です。

Workerは応答の要求ID・局面識別子・エンジン版・探索予算を照合します。現在の局面で合法と確認した着手を保存し、次のAlarmで局・局面・時計を再確認して適用します。応答が使えない場合は既存のLv2で対局を続けます。入玉宣言と持将棋の判断はGameRoomで行います。

開発用イメージを1/16 vCPU・256MiBで起動したローカル統合試験では、2つの将棋ルームが同時に実エンジンへ要求し、それぞれ合法手を反映しました。タイムアウト時の代替手と、応答待ちに持ち時間が切れた場合の終局も確認しました。同じイメージで将棋と四人リバーシのAI Service統合テスト計37件が通り、メモリの最大は約144MiBでした。Cloudflare上での起動・応答時間と四人リバーシとの同時負荷は未確認です。

### 2026-11-09の予備測定

[やねうら王のコミット `faeb37f0`](https://github.com/yaneurao/YaneuraOu/commit/faeb37f08b63fd1fd99fd18512fcdeb945975c21)の `YANEURAOU_ENGINE_MATERIAL`、`MATERIAL_LEVEL=001`（MaterialLv1 9.80git）を使用しました。外部の評価ファイルと定跡は使用せず、上流の本体ライセンスがGPLv3であることを確認しました。1スレッド、ハッシュ16MiB、`BookFile=no_book`、`EnteringKingRule=NoEnteringKing` とし、着手履歴をUSIで渡して `go nodes` の予算を変えました。

macOS 27.0.1 arm64、Apple clang 21、Bun 1.4.4で、探索予算64・512・4096の各ペアを12局ずつ比較しました。6種類の序盤を通常将棋の合法手列からseed 100〜105で作り、それぞれ先後を入れ替えて対局しました。着手と勝敗の判定にはTetraBoardの通常将棋ルール（`e31594a9`）を使用しました。

| 探索予算の比較 | 高予算側の勝ち | 低予算側の勝ち | 引き分け |
| -------------- | -------------: | -------------: | -------: |
| 64対512        |             10 |              2 |        0 |
| 64対4096       |             12 |              0 |        0 |
| 512対4096      |             12 |              0 |        0 |

全36局が詰みで終局し、エンジンが返した3,086手はすべて合法でした。MacでのUSI要求から `bestmove` までのp95は、64・512・4096ノードの順に0.23・0.40・2.06msでした。固定探索予算による予備対局のため、5分＋30秒での人間との棋力較正と、各段階の基準レートは未確認です。

同じソースをGCC 14.3.0（`TARGET_CPU=SSE42`）でビルドし、Apple Silicon上のローカルDockerでlinux/amd64、1/16 vCPU、256MiB、スワップなしを指定しました。3局面を使い、各要求前に `usinewgame` と `isready` を送った単独プロセスの試験では、各予算30要求、計90要求に応答しました。`readyok` までのプロセス起動時間は2.40秒でした。

| 探索予算 | 着手応答のp50 | 着手応答のp95 |     最大 |
| -------: | ------------: | ------------: | -------: |
|       64 |        0.82ms |       98.43ms | 195.57ms |
|      512 |        1.60ms |       96.18ms | 100.90ms |
|     4096 |      100.94ms |      198.85ms | 199.17ms |

同じ初期化手順で2プロセスを同時に動かすと、ハッシュ16MiB・4MiBの両方でメモリ上限に達し、OSがエンジンを終了させました。対局ごとの初期化を各プロセスの初回だけにした16MiBでの再試験でも、メモリ上限による強制終了を確認しました。

この段階では、ローカルコンテナ内のUSI応答を測りました。Cloudflareでのコンテナ冷起動と、既存のAI Serviceと共用した場合の容量は未確認です。

### 1プロセスに複数対局の要求を渡す試験

前項と同じlinux/amd64、1/16 vCPU、256MiBのローカルDockerで、起動済みのエンジン1プロセスにHTTP要求を順番に渡しました。エンジンの版と設定は前項と同じで、探索予算は4096ノードです。通常将棋のルールから作った8種類の棋譜を使い、各要求に開始からの着手履歴を渡しました。同時要求数ごとに24回の試行を行い、同じ試行内では別々の棋譜を使いました。

| 同時要求数 | 応答件数 | HTTP応答のp95 | HTTP応答の最大 | エンジンを待った時間のp95 |
| ---------: | -------: | ------------: | -------------: | ------------------------: |
|          1 |       24 |      199.24ms |      2000.44ms |                    0.46ms |
|          2 |       48 |      294.97ms |       299.53ms |                   99.00ms |
|          4 |       96 |      398.64ms |       500.99ms |                  295.99ms |

全168件で要求IDが一致し、応答はその棋譜の合法手でした。タイムアウトとメモリ超過は0件です。コンテナ内でエンジンを起動して `readyok` を受けるまで2.30秒、計測用のHTTPサーバーとクライアントも含めたメモリの最大は約189MiBでした。Cloudflareでの起動、Workerからの通信、四人リバーシAIと同居した場合の性能は別途確認します。

### CPU同士の暫定基準レートの測定

予備測定と同じmacOS環境・エンジン・通常将棋ルール（`e31594a9`）で、探索予算64・128・256・512・1024ノードの全10組を比較しました。seed 200〜235を使い、初期局面から合法手を6手指して序盤を作りました。各手で乱数を `(1664525 × 前の値 + 1013904223) mod 2^32` で進め、合法手数で割った余りを `getLegalActions` の添字にしました。各組で同じ序盤から先後を入れ替えて2局ずつ指しました。先手と後手にそれぞれエンジンを起動し、対局開始ごとに探索状態を初期化しました。

seed 200〜223の480局を基準値の推定に使用し、224〜235の240局を評価用に分けました。256ノードを1500に固定し、勝ちを1、引き分けを0.5、負けを0とする結果に、全組のElo期待得点を当てはめました。序盤のseed単位で1,000回再標本化し、暫定値の95%区間を求めました。

| 探索予算 | 暫定基準レート |        95%区間 |
| -------: | -------------: | -------------: |
|       64 |           1304 |     1202〜1387 |
|      128 |           1352 |     1281〜1415 |
|      256 |           1500 | 基準として固定 |
|      512 |           1613 |     1541〜1689 |
|     1024 |           1764 |     1695〜1845 |

720局すべてが終局し、エンジンが返した83,331手はすべて合法でした。評価用240局の期待得点の平均二乗誤差は0.148で、全局を互角（期待得点0.5）とした場合の0.234を下回りました。この差の95%区間は序盤単位の再標本化で0.055〜0.114でした。表の値は固定探索予算によるCPU間の比較結果で、人間との対戦や、複数対局が1プロセスの探索状態を共有した場合の棋力は確認していません。

### 共有プロセスでの暫定値の再評価

同じmacOS環境で、評価用の240局を実AI Serviceの `/v1/shogi/move` 経由で再実行しました。1プロセスで4局ずつ進め、全28,575手が合法でした。全10組で探索予算が大きい側が勝ち越しました。前項の暫定レートを当てはめた平均二乗誤差は0.186で、全局を互角とした場合は0.249でした。個別プロセスでの0.148より誤差が増えたため、暫定値は開発検証の目安とします。
