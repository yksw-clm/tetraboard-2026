# 四人将棋のCPU補充レート戦（導入案）

四人将棋を四人リバーシと同じ4人制のレート戦に接続する案です。比較元は `origin/develop` の `0e111b75` にある [四人リバーシのレート戦](matchmaking.md) です。

2026-11-10に、登録アカウント向けのシングルス、三人攻撃禁止ON、1人3分切れ負け、人間優先、待機20秒でのCPU補充試行を初回の条件として開発者が承認しました。

| 項目 | 四人将棋の初回導入案 |
| --- | --- |
| 参加条件 | 登録アカウント。シングルス、三人攻撃禁止ON、1人3分切れ負け。 |
| マッチング | 先に人間を最大4人集め、待機20秒で不足席をCPU補充。補充枠が埋まっている間は元の待機順で対人成立と枠の再取得を待つ。上位帯も共通ルールを適用。 |
| CPUの選び方 | 認定済み参加者の実力推定の中央値に最も近い較正済み設定を使い、全員が認定中なら中間の設定を使う。同じ卓の補充席は同じ設定にそろえる。人間の推定が最強CPUの基準値を超えていれば最強の較正済み設定を使う。 |
| 認定と更新 | CPU混在を含めた最初の有効5局で認定。以降も混在局と対人4人局で同じ公開レートを更新する。対人戦の経験有無を示す補足ラベルは表示しない。 |
| 算出 | GameRoomが確定した1〜4位と同順位をOpenSkillのPlackett–Luceへ渡す。CPUの較正値を固定し、人間側だけを更新する。認定後はCPU入りで±24、人間4人で±32を上限とする。 |
| AI障害 | 一時障害は応答期限内で1回再試行する。合法な代替手を使った局は認定・レート更新から除外する。CPU設定と較正版、代替手の有無を対局に記録する。 |

補充CPUは、[Rust版Lv3の着手API](../packages/ai/README.md#四人将棋の着手api)で、1手あたりの探索作業量を変えた3設定を使います。作業単位は局面展開や合法手の処理などの費用を数えるカウンターです。予備比較では4,096・16,384・65,536作業単位を比較し、実際の処理量と500msに達した割合を記録しました。

レート戦用のAI Serviceで使う設定を固定し、実際の探索予算、ルール、エンジン版、設定hashを測定結果にひも付けます。CPU同士の混成対局で相対値を求め、強さを分けられた設定を補充候補にします。続いて、同じルールと持ち時間の開発試験で対人の期待順位と実際の順位を照合します。上級者より弱いCPUの基準値は実測に合わせ、上級者との対局でもその値を入力します。

ダイアログの待機人数は、有効な人間の待機者と利用可能なCPU枠を加算する[共通仕様](../README.md#レート戦の待機人数)に従います。CPU枠が未使用で人間の待機もなければ12人です。開始前の予約と同時対局数の上限も反映します。

検索中の残り時間の目安・見積もれない場合の経過時間は、[マッチング時間の共通仕様](../README.md#レート戦のマッチング時間の目安)に従います。

## 実装順序

1. **対象と作業ブランチを確定する。** 承認済みの対局条件をREADMEと[四人将棋のルール正本](rules/four-shogi.md)に記録します。AI Serviceの実装ブランチは `develop` の `0575307b` を基点とします。

2. **四人将棋の着手をAI Serviceから返せるようにする。** `POST /v1/four-shogi/move` は棋譜を再生し、探索作業上限4,096・16,384・65,536と共通の500msでRust版Lv3の候補手を返します。応答にはエンジン版・設定識別子が含まれます。GameRoomは手順4で接続し、正本のTypeScript側で合法手と終局を確定します。ローカルでは代表3棋譜の297局面で手番・合法手一覧・順位と終局結果を照合し、3設定とも実Serviceから合法手が返ることを確認しました。[着手API](../packages/ai/README.md#四人将棋の着手api)

3. **補充CPUを較正する。** 48局の予備比較を基に、採用判断用の対局は別の開始局面と相手構成を使い、席を均等に入れ替えます。3分の時計にCPUの共通待機と処理時間を計上し、順位、時間切れ、探索量、応答時間、500ms到達率を記録します。CPU同士の順位から固定の参照値を作り、較正に使わなかった対局で順位の予測を検証します。実Serviceでも同時実行時の応答とタイムアウトを測定します。65,536と16,384を区別できなければ、その差をレートに反映せず、区別できた設定だけを採用します。CPU同士の相対値と人間の尺度とのずれは開発試験で別に確認します。

4. **共通レート戦に四人将棋を登録する。** 共通のプロトコル、待機列、参加枠、補充枠管理に四人将棋を追加します。専用の待機列キーを使い、人間を優先して20秒で不足席の補充を試みます。卓に割り当てたCPUの設定・較正版・参照値を開始時に保存します。GameRoomではCPU応答の適用時に局ID・局面リビジョン・手番・期限を再確認し、異常時は合法な代替手で続行した事実を記録します。共通レート保存を使い、四人将棋の履歴と確定順位から人間だけを更新します。対局保存とレート反映を再試行しても同じ対局は一度だけ反映します。完了条件は、人間1〜4人での成立、上位帯での補充、CPU枠の満杯と解放、期限切れ、AI障害、同順位、認定5局目、重複再送をWorker統合試験で確認できることです。

5. **ロビーから対局結果と再参加までつなぐ。** 共通のレート戦ダイアログ、認定表示、待機・取消・自動入室、対局結果、再参加の入口を四人将棋へ接続します。CPUを明示し、ゲーム別の公開レート、認定中の進捗、レート更新除外の理由を表示します。完了条件は、共通UIのテストに加え、開発環境で検索から結果確定後の再参加まで通せることです。既存の将棋・四人リバーシでも同じ導線の回帰を確認します。

6. **開発環境で運用を確認してから公開を判断する。** 必須ローカル検証とFull CIを通した後、開発環境で実Serviceを接続し、混在局と人間4人の局を確認します。実測を基にCPUの採用設定、公開レートの換算、AIの同時対局枠を決めます。公開判断には較正結果、応答時間・障害時の代替手の発生率、費用、受付停止手順をそろえます。停止操作では新規参加の受付を止め、成立済みの対局と結果の保存を完了できることを確認します。

CPU接続と較正、待機列とレート保存、画面と開発公開の順でレビューします。CPU候補の較正中も共通基盤への接続は進められます。CPU補充を有効にした開発試験には、版が一致する較正済み設定が必要です。

追加対局を回す前に、対局数と設定を分けるための判定基準、サービスの応答時間の目標を決めます。CPU同士の結果で分かるのは設定間の相対差までです。人間と混在する開発試験で期待順位と実績を照合し、人間側のレート尺度に載せる参照値を決めてから、本番でCPU混在局をレートに反映します。

## 補充CPUの名前

名前・アイコンから開くプレイヤー情報には、レート戦の成立時に固定した対局前レートを表示し、棋譜でも同じ値を使います。CPUはその局の基準レート、認定前の登録者は「認定中」とします。通常ルーム・大会では表示しません。過去の記録と現在プロフィールの区別は[プレイヤー情報の共通仕様](../README.md#プレイヤー情報カード)に従います。終局結果の更新後レートと増減は従来どおりです。

新規ルームでは、探索の作業上限4,096を「ヨツメ」、16,384を「シテン」、65,536を「カコイ」と表示します。CPUが1席なら名前だけを使い、複数席なら補充順に1から番号を付けます。ルームのカードには名前と「CPU」を表示し、入室メッセージ、プレイヤー情報、終局結果、棋譜にも同じ名前を使います。

## 開発環境の確認手順

四人将棋は専用の待機列とD1のレートテーブルを使い、専用AIコンテナとCPU予約枠を持ちます。開発環境向けの `FOUR_SHOGI_MATCHMAKING_ENABLED=true` と既存のAI Service接続設定で新規受付が有効になります。着手APIを含むAI ServiceとD1の `0037_four_shogi_rating.sql` を先に反映してから、アプリWorkerを反映します。

1. 登録アカウントで四人将棋ロビーの「レート戦」を開き、一人で待機します。20秒でCPU3席の補充を試みます。全員接続とAI準備完了がそろったら、5秒のカウントダウンで対局が始まります。認定中のアカウントではCPU名は「シテン1」「シテン2」「シテン3」です。
2. 三人攻撃禁止ON、1人3分切れ負けで合法なCPU着手が進むことを確認します。終局後に結果画面の認定局数またはレートを確認します。本人向けの `GET /api/matchmaking/four-shogi/results/:matchId` と `GET /api/matchmaking/four-shogi/rating` でも確認できます。
3. 「もう一度マッチング」で次の待機列に入れることを確認します。AI障害を再現した局は、棋譜が保存され、結果が `excluded / ai_fallback` になります。

ローカルの実AI Service付き統合試験では、CPU補充、着手、終局、棋譜保存、認定局数の反映、代替手を使った局の除外、保存待ちの解放を確認します。公開用の基準レートと65,536の採用は、人間との混在対局で確認します。

開発環境のCloudflare Workers Logsでは、`four_shogi_queue_accepted` と `four_shogi_assigned` を `diagnosticId` で照合し、以降は `matchId` で `four_shogi_connected` と `four_shogi_started` を追います。接続が切れてカウントダウンをやり直すときは `four_shogi_countdown_reset` を挟みます。CPU枠の待機は `four_shogi_cpu_capacity_wait` に記録されます。

AI障害は `four_shogi_ai_attempt_failed` の `requestId` と `attempt` で開発用AI Workerの `four_shogi_ai_gateway_failed` と照合します。復旧後の着手は `four_shogi_ai_retry_applied`、代替手の使用は `four_shogi_ai_fallback_applied` で確認できます。検証時は専用コンテナの停止後に1局開始し、人間が途中で10秒以上考えた後もCPUが着手することを確認します。終局後に認定進捗とログを照合します。準備の開始・完了・失敗は `four_player_ai_warmup_*` を対局IDで検索します。

## 探索量別の追加比較（2026-11-10）

予備比較とは別の24開始局面（seed 7300000〜7300023、序盤8〜14手）から、各12局、計288局を実行し、すべて終局しました。各開始局面で3設定を同卓に置き、2席を占める設定と席順を交代しました。三人攻撃禁止ON、1人3分切れ負けで、序盤の後から各手に固定待機2秒と実測の探索時間を計上しました。探索の打ち切りは全設定500msです。macOS arm64のRust 1.99.1 release、8並列で計測しました。基点は `0575307b` で、未コミットのRust実装と実行ファイルのハッシュを測定資料に含めます。

過去に保存した98種類の開始局面との重複がないことを確認し、全37,522イベントをGameRoomと同じTypeScriptルールで再生しました。手番・着手・終局理由と順位、時計の集計が一致しました。

| 1手の作業上限 | 平均順位 | 1位（同率含む） | 時間切れ | 探索時間 p95 | 暫定基準レート |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4,096 | 2.75位 | 37 / 384席 | 2 / 384席 | 36.7ms | 1,437（1,401〜1,469） |
| 16,384 | 2.42位 | 101 / 384席 | 7 / 384席 | 127.9ms | 1,500（固定） |
| 65,536 | 2.26位 | 169 / 384席 | 12 / 384席 | 500.0ms | 1,549（1,504〜1,598） |

順位得点は相手より上位なら1点、同順位なら0.5点です。95%区間は開始局面ごとに5,000回再標本化して求めました。区分の判定基準は、隣り合う設定の順位得点率が55%以上、95%区間の下限が50%超、独立した72局でも優劣の方向が逆転しないことです。

| 比較 | 全288局の順位得点率（概算95%区間） | 独立72局の順位得点率 |
| --- | ---: | ---: |
| 16,384 対 4,096 | 59.4%（55.1〜63.5%） | 62.1% |
| 65,536 対 16,384 | 55.6%（50.9〜60.6%） | 52.5% |
| 65,536 対 4,096 | 62.4%（56.7〜67.8%） | 57.1% |

暫定レートは、216局のペア順位得点率にOpenSkillの2者間予測式を最小二乗で合わせ、`sigma=1` として16,384の `mu=25` を1,500に固定しました。換算は四人リバーシと同じ `1500 + 50 × (mu - 25)` です。区間は較正に使った開始局面単位の再標本化によります。対局順にOpenSkillの順位更新を適用する方法も試しましたが、65,536と16,384を逆順に推定し、独立72局の平均二乗誤差は0.2496でした。順序に依存しないペア当てはめの誤差は0.2377、常に50%と予測した場合は0.2417です。改善量の95%区間は−0.0119〜0.0200で、独立局での改善と人間のレート尺度への対応は引き続き確認が必要です。

別途、ローカルAI Containerに45局面を各設定で送り、同時1件・4件の合計270応答を確認しました。失敗は0件で、同時4件のHTTP応答p95は4,096が19ms、16,384が92ms、65,536が310msでした。試験目標はp95が750ms以内、5秒の期限切れ0件です。対局中に65,536が探索打ち切りの500msに達したのは724 / 11,804手（6.1%）です。クラウド上の処理能力は開発環境で別途測ります。

開発試験には4,096を低め、16,384を標準として採用できます。65,536は区分基準を通過しましたが、独立局での上積みが小さく、探索時間と時間切れが増えました。最強枠の候補として開発試験に残し、公開時の採用は人間との混在対局とクラウドでの応答時間を確認して決めます。

## 探索量別の予備比較（2026-11-10）

同じLv3を使い、各卓に4,096作業単位を1体、16,384を2体、65,536を1体置きました。未使用の12開始局面で席を入れ替え、三人攻撃禁止ON・3分切れ負け・固定待機2秒＋探索実時間で48局を実行し、全局が終局しました。1手の探索時間上限は共通で500msです。

| 1手の作業上限 | 平均順位 | 探索時間 p95（ローカル） |
| ---: | ---: | ---: |
| 4,096 | 2.83位 | 37ms |
| 16,384 | 2.39位 | 117ms |
| 65,536 | 2.27位 | 490ms |

16,384の4,096に対する順位得点率は63.5%（開始局面単位の概算95%区間54.7〜72.9%）でした。65,536の16,384に対する得点率は55.7%（46.9〜65.1%）で、上位2設定の棋力差は追加測定が必要です。65,536は1,202手中55手で500msに達しました。数値はローカルの同一構成内の比較です。採用する設定は、実Serviceでの探索量と、別の開始局面・相手構成での棋力を確認して決めます。集計は `four-shogi-lv3-tier-pilot.json`、棋譜は `four-shogi-lv3-tier-pilot-replays.jsonl` に記録しています。

## 参考測定（2026-11-10）

Lv3の500ms版と2秒版を、三人攻撃禁止ON・3分切れ負けで比較しました。各卓は2秒版1体と500ms版3体です。新規8開始局面で2秒版の席を4方向に替え、時計条件ごとに32局を実行しました。設定した序盤手順の後から時計を計測し、全64局が終局しました。

| 時計に計上した時間 | 2秒版の順位得点率 | 開始局面単位の概算95%区間 | 時間切れ（2秒版 / 500ms版） |
| --- | ---: | ---: | ---: |
| 探索実時間 | 56.3% | 44.8〜65.6% | 2/32席 / 0/96席 |
| 固定待機2秒＋探索実時間 | 55.7% | 43.8〜67.2% | 8/32席 / 1/96席 |

順位得点は500ms版1体ごとに、上位なら1点、同順位なら0.5点です。完了した探索深さの中央値は、両条件とも500ms版が4、2秒版が5でした。2秒待機は時計上だけで再現しました。ローカルでの時間予算比較で、Cloudflare上の性能や本番用のCPU基準レートを測定したものではありません。集計は `four-shogi-lv3-clock-trial.json`、棋譜は `four-shogi-lv3-clock-trial-replays.jsonl` に記録しています。
