# TetraBoardの構成

この文書は技術構成と状態の置き場所を記す。ゲーム共通の利用仕様は `README.md`、ゲーム固有のルールは `docs/rules/four-reversi.md` と `docs/rules/four-shogi.md` を正本とする。

## 採用する構成

- 開発環境はBunに統一し、Bun Workspaceでフロントエンド、サーバー、共有コードを管理する。実際のパッケージ配置は実装開始時に決める。
- フロントエンドはVite、React、TypeScriptで作る。
- 本番の `tetraboard-2026` WorkerでViteのビルド成果物をStatic Assetsとして配信する。画面はSPAフォールバックを使い、`/api` と `/api/*` はWorkerを先に実行する。Honoは `/api` 接頭辞付きと既存のWorker直接アクセスの両方を扱う。HTTP APIとWebSocketは画面と同じオリジンを使う。
- サーバーはCloudflare Workers上のTypeScriptで作る。HTTPのルーティングにはHonoを使う。HTTPとWebSocketの入口を担当し、ルームIDに対応するDurable Objectへ処理を渡す。
- WebとWorkerの境界を通るデータのスキーマ、型、エンドポイント定義は `packages/protocol` に置く。四人リバーシの純粋な判定ロジックは `packages/four-reversi` に置き、通信契約と混在させない。
- 四人将棋の純粋な判定ロジックは独立した `packages/four-shogi` に置く。盤面・持ち駒・手番・脱落・三人攻撃履歴・反復回数をJSONで保存できる状態として管理する。時刻、通信、参加者の担当抽選は呼び出し側で扱う。Web・Worker・protocolへ接続し、合法手と受理した局面をサーバーから配信する。
- ルームごとに1つのDurable Objectを使い、参加者、対局進行、持ち時間、チャットと接続を管理する。ゲーム固有の合法手・終局判定は、ルーム管理から分離したTypeScriptのロジックとして扱う。
- CPUの着手候補の選択は `packages/four-reversi` の純粋なロジックで行う。Durable Objectが選択を起動し、通常の着手と同じエンジンで確定・保存・配信する。
- 四人将棋のCPUは `packages/four-shogi` 内の `cpu.ts` に選択処理、`cpuEvaluation.ts` に静的評価を分ける。公開API `chooseCpuAction` は既存の合法手と着手処理を使い、ルール状態や保存形式を増やさない。Lv1の乱数は注入可能とし、Lv2は上位8候補・応手16件の制限と列挙順によって決定的に選ぶ。時刻による探索打ち切りを設けず、Durable Objectが思考を起動する。選択結果を保存して次のAlarmで局ID・revision・手番・期限を検査してから適用する。
- 公開ロビーのルーム索引、通報、アカウントと認証セッション、利用状況の計測はD1に保存する。通報には確認に必要な部屋IDも含む。両ゲームの終局データと本人の履歴をD1に保存し、ゲーム別の戦績・ランキングを集計する。将棋の棋譜は初期化情報と連番イベントを分けて保存し、部屋内の直前1局と恒久保存待ちを独立して管理する。

## ロビーとゲームテーマ

- 四人リバーシと四人将棋のロビーは `features/lobby/LobbyView` でレイアウト・入口・ダイアログ表示を共通化する。ゲームごとの見出し・説明・遊び方・盤面プレビューを切り替え、公開ルームとランキングはページ側から渡す。両ゲームのランキングは画面幅による表示順の変更でも状態を保持する。
- 両ゲームが `useLobby`・`useRoomEntry` を利用し、公開一覧と作成にゲーム指定を付ける。省略時はリバーシとして従来の通信を維持する。ランキングもゲーム別のAPIを使い、共通のカード・詳細ダイアログで表示する。
- 共通ヘッダー直下のゲーム選択は両ロビーだけに配置し、`NavLink` でURLと選択状態を一致させる。トップURLからの転送先はリバーシを維持する。
- 緑の共通テーマを既定とし、将棋の内容だけに `game-theme-four-shogi` を適用する。主要ボタンの塗り・文字色と文字アクセントを別トークンにし、黄色のボタンには濃い文字を使う。ヘッダーとアカウントメニューはゲームのテーマ範囲外に置く。
- Portalで表示する入力・遊び方・ランキングのダイアログには `AppDialog.theme` でテーマを明示する。共通のアカウントダイアログは既定の緑を維持し、ゲームを切り替えてもグローバルなテーマ状態を変更しない。

## ルーム状態と再起動

- 対局中の正本はルームのDurable Objectが持つ。再起動や休止でメモリは消えるため、復元が必要な部屋の状態を、そのDurable Objectに付属するSQLiteストレージへ保存する。対局状態をD1に複製しない。
- 盤面、手番、参加者、持ち時間の基準時刻、復帰期限などは、状態が変わったときに保存する。秒ごとの残り時間表示を保存処理にしない。起動時には保存済みの状態を読み、進行中はメモリで扱う。
- WebSocketはDurable ObjectsのHibernation APIを使う。通常の休止では接続が維持されるが、メモリ上の状態は再生成される。
- デプロイ時にはDurable Objectが再起動し、WebSocketが切断される。クライアントは再接続を試み、サーバーは保存済みの状態から部屋を復元する。復帰の扱いと持ち時間の進行は `README.md` に従う。MVPでは、サーバー再起動後の対局継続を可用性の保証対象とはしない。
- 持ち時間切れや復帰期限などの判定は、保存した基準時刻と期限から行う。色ごとの残り基本時間と現在の手番の開始時刻・期限をSQLiteに保存し、GETとWebSocketのスナップショットには送信時のサーバー時刻を添える。Webは受信時刻からの経過時間で表示を進め、秒ごとの書き込みはしない。最も早い時計・復帰期限に単一のDurable Object Alarmを設定し、遅れた場合は保存期限の時刻順に処理する。同時刻は時間切れを先に処理する。
- CPUの手番では同じAlarmに着手予定時刻も登録する。手番開始から約0.5秒後に着手し、処理が遅れた場合も持ち時間の期限を先に確定する。CPUにはWebSocketや復帰期限を設けない。人間の参加者が全員退室または復帰期限切れになると、脱落処理で終局した場合は保存し、未決着ならCPUの進行を止めて部屋を閉鎖する。脱落後の在室者と復帰待ちは部屋を維持するが、通常の観戦者は維持条件に含めない。閉鎖で現在局の棋譜と将棋のCPU選択を破棄し、過去の終局済み保存待ち・保護棋譜と必要な再試行Alarmは保持する。
- 作成・入室から最初の接続までと、最後の認証済みWebSocketの切断から30秒の復帰期限を、プレイヤーごとにSQLiteへ保存する。同じ資格の接続が他に残っていれば期限を開始しない。切断通知が届かなかった場合は、次のルームアクセス時に接続の欠落を検出して期限を開始する。期限の早い順、同時刻なら入室順に処理し、最も早い期限へ単一のアラームを設定する。アラームの遅延に備え、ルームの取得・認証・操作時にも保存期限を照合する。
- ルームが閉じたら付属ストレージの部屋状態を削除する。索引用の更新番号と反映待ち情報は、閉鎖情報の反映と部屋番号の再利用に必要な間保持する。チャットの保存期間と通報データの扱いは `README.md` に従う。
- 対局開始時にDOの `round-replay` に初期局面と対局識別子を保存し、着手・脱落の種類と原因、確定した局面、自動パスの色順を対局状態と同じトランザクションで追記する。対局中の棋譜全体は配信しない。終局時に記録を `lastRound.replay` へ移して最終盤面・結果とともに直前1局分だけ保持し、待機状態へ戻す。ホストの操作なしに再戦の準備が始まり、次の対局開始時に前局情報を消す。Webは保存された局面とパス順から閲覧用の項目を作り、選択状態は各閲覧者の画面内で保持する。再読み込みは最終項目から表示する。旧保存状態の `lastRound` に棋譜がなければ `null` として読み、最終盤面のみ表示する。直近100件のチャット（システムログを含む）は別のDO状態として保持し、盤面更新のたびに再配信しない。
- 最終活動から24時間の閉鎖期限も既存の単一Alarmに含める。閲覧と再接続では活動時刻を進めない。

## 部屋の指定と検索

- 招待URLは部屋番号と既存の `instanceId` を含み、参加資格トークンは含めない。Webは取得した部屋の識別子を照合してから表示する。
- 参加APIは任意の `instanceId` を受け取り、Durable Objectが席を追加するトランザクション内で照合する。不一致は `room_changed` / HTTP 410とし、従来の番号だけの参加も受け付ける。WebSocketも任意の識別子を接続前に照合する。Webは初回取得した識別子を再接続と受信スナップショットでも確認し、別の部屋への切替を停止する。
- ロビーとルームは参加リクエスト・応答検証・参加資格保存を共通化する。同じタブの有効な参加資格は再利用する。ルーム内で参加したらloaderを再実行し、部屋識別子と参加者IDをキーに観戦接続から本人の接続へ切り替える。
- すべての部屋を公開対象とし、公開・非公開の設定は持たない。公開ロビー用の情報は部屋ID、ゲーム種、対局モード、固定の持ち時間、状態、現在のホスト名・アイコン、人間・CPUの席数、定員・空席数、公開情報の更新時刻とする。対局開始後の席数は、脱落・退室にかかわらず開始時の参加者構成を表す。ホストが退室して後任がいなければホスト名は空にする。
- 公開ロビーの一覧はD1のルーム索引から取得する。各Durable Objectを一覧表示のたびに巡回しない。索引には一覧に必要な公開情報だけを置き、盤面、各人の残り持ち時間、チャットは置かない。
- ルームのDurable Objectを状態の正本とする。部屋の作成、参加・退室、CPU席やモードの変更、対局の開始・終局後の再戦待機、部屋の閉鎖など、公開情報が変わるときだけ更新時刻を進める。通常の着手では進めない。終局後の部屋は待機中としてロビーに表示する。
- 公開情報の変更時に、Durable Objectの付属SQLiteへ状態と索引への反映待ち情報を更新番号付きで同一トランザクションに保存し、その後D1へ反映する。D1への反映が失敗した場合は既存のアラームで再試行する。更新番号を比較して古い更新が新しい表示を上書きしないようにし、閉鎖時はD1に閉鎖記録を残して一覧から除外する。部屋番号の再利用後もDO内の更新番号を引き継ぐ。
- 異なる保存先を同時に確定できないため、ロビーの表示が一時的に古くなることはある。参加・観戦の可否は対象のDurable Objectで最終確認する。

## データの役割

| 場所 | 主なデータ |
| --- | --- |
| ブラウザ | 画面の一時状態、受信したルーム状態、残り時間の表示、タブ内の参加資格トークン |
| ルームのDurable Objectと付属ストレージ | 対局の進行状態、参加者、期限、部屋内の一時チャット |
| D1 (`APP_DB`) | 公開ロビーのルーム索引、通報、アカウント、認証セッション、画像削除待ち、アカウント席予約・ルーム画像参照、利用状況の計測データ、両ゲームの終局データ・本人別履歴・将棋の棋譜イベント |
| R2 (`OBJECT_STORAGE`) | プロフィールのアイコン画像 |

通報されたメッセージの保持と削除は `README.md` のチャット仕様に従う。

通報はメッセージ本文と部屋の世代IDをD1に記録する。運営者APIは秘密トークンで保護し、処分の対象が同じ世代の部屋かをDOで確認する。7日を過ぎた通報をAPIから除外し、Workerの毎時実行でD1の期限切れ行を削除する。

部屋ごとの参加資格トークンはブラウザの `sessionStorage` に保持する。Durable ObjectはトークンのハッシュとプレイヤーID・役割を付属ストレージに保存し、公開ルーム情報とWebSocketには資格情報を含めない。本人の役割はWorker経由でDurable Objectがトークンを検証して返す。D1には参加資格を保存しない。

## アカウントの認証と保存

Better Auth 1.7.5でGoogle OAuthを処理する。Workerはログイン開始・Googleコールバック・ログアウトだけを公開し、プロフィールを汎用の認証APIから変更させない。認証用Cookieは `tetraboard-2026` 接頭辞とHttpOnly／SameSiteを使い、本番ではSecureを付ける。認証・プロフィールの応答は `no-store` とし、更新元は設定済み `APP_ORIGIN` と一致するOriginだけを受け付ける。Workerの `nodejs_compat` はBetter Authの実行に使う。

D1の名前・IDは変えず、接続名だけを `LOBBY_DB` から `APP_DB` へ変更する。追加マイグレーションで旧版互換の `user`・`account`・`session`・`verification` と `rateLimit`・`avatar_deletions` を作る。IDの大文字・小文字を無視した一意索引と、Google識別子の一意索引で競合を拒否する。セッションはD1で本人を確認し、プロフィールは毎回DBから取得する。期限切れの認証用一時データは毎時削除する。

WebはCanvasのWebP出力が使える場合は標準機能を使い、使えないWebKit系では `@jsquash/webp` 1.5.0のJS／WASMを遅延読み込みして端末内で変換する。WASMも同じWorkerの静的資産として配信し、画像を変換サービスへ送らない。

新しいアイコンをR2へ保存後、名前・ID・画像参照と旧画像の削除待ちをD1 batchで更新する。D1が拒否した場合は新画像を削除し、旧参照を維持する。同時の画像編集は読み取った旧キーを更新条件にして競合を検出する。保存成功後と毎時の処理で、プロフィール・ルームのどちらからも参照されない削除待ち画像をR2から削除する。画像キーは `avatars/<UUID>.webp`、配信URLは `/api/avatars/<UUID>` とし、旧版のキーをコピーして利用できる。

入室時にWorkerがCookieの本人を確認し、最新プロフィールを取得する。GameRoomは名前・アイコンを公開プレイヤー情報へ保存し、内部ユーザーIDと席の対応は非公開の `seat-account:<playerId>` に保存する。ルーム操作・再接続は従来の参加トークンで認証し、入室後のログイン・ログアウト・プロフィール変更で席を付け替えない。

D1の `account_room_seats` はアカウントIDを主キーにし、全ルームで1席を保証する。操作ID・部屋番号・世代ID・プレイヤーID・プロフィールのスナップショットを予約時に保存する。画像がある場合は `room_avatar_refs` への参照登録を同じD1 batchで行い、取得時の名前・画像キーとDBの現値が一致する場合だけ予約する。外部URLは公開・移行せず、アイコン未設定とする。

GameRoomは入室確定のD1照合とDO保存を `blockConcurrencyWhile` で直列化する。中断予約は30秒後から回収対象にするが、確定した席は予約の年齢だけでは解放しない。DOで占有状態を照合し、不在なら取消を永続化してから操作IDを条件にD1の予約を削除する。取消と入室確定を直列化し、遅延したRPCによる席の復活を防ぐ。毎時の回収は最終確認時刻順に最大100件を調べ、確定済みの席ばかりを調べ続けない。

退室・復帰期限切れ・閉鎖で、席予約の解放待ちをDOの状態変更と同じトランザクションで保存する。D1反映失敗は5秒後のAlarmで再試行し、操作IDと世代IDによって古い解放処理が新しい席を削除しないようにする。投了・時間切れだけでは占有を解除しない。脱落後のアカウント席にも接続期限を適用するが、脱落を二重に処理しない。解放済みの席は、元トークンで閲覧しても再戦へ戻さない。

画像参照は占有解除と独立して保持する。対局中の退室・期限切れでもカードが残る間は画像を保持し、プレイヤーが待機席から削除された時または部屋閉鎖時に参照を解放する。プロフィール画像はUUIDごとに不変なのでコピーは不要で、既存の画像削除処理がルーム参照も確認する。

## 四人将棋のルーム保存と表示

`Room` は `FourReversiRoom | FourShogiRoom` とし、`settings.game` で判別する。席管理・参加資格・アカウント予約・通信・期限管理は共通のGameRoomに残し、将棋の時計・保存・エンジン呼び出しを分ける。リバーシのJSON形式を維持し、将棋の局ID・方向・revision・設定を追加する。

将棋は付属SQLiteに通常状態、局ID・局面キー別の反復回数、初期化情報と着手／外部脱落の連番イベントを分けて保存する。受理した局面と反復回数・イベント・revisionは同一トランザクションで確定する。通常配信に反復回数を含めず、サーバー算出の合法手を同じrevisionで配信する。イベントの棋譜を100件ずつ取得し、Webがエンジンで再生する。部屋からは直前1局だけを取得可能とする。次局開始・部屋閉鎖でもD1未保存の棋譜は保持し、保存待ちが解消した不要な行を削除する。[DOの保存上限](https://developers.cloudflare.com/durable-objects/platform/limits/) を踏まえ、毎手の全履歴複製を避ける。

CPU選択はゲームルールから分離した純粋関数を使う。将棋の思考結果は局ID・revision・手番とともに保存し、次のAlarmで期限を確認してから確定する。[同期処理中は時刻が進まない](https://developers.cloudflare.com/workers/runtime-apis/performance/) 本番でも、思考時間を持ち時間に含める。

外側のルーム配置・タブ・チャット・招待・ダイアログ・時計表示・棋譜操作とカード表示を共有する。将棋の盤面と持ち駒は専用部品を使い、自陣営を下へ置く座標変換と共通の駒描画で4方向・同縮尺に対応する。

## ゲーム別の履歴・戦績と保存棋譜

D1の `matches` と `account_match_history` を両ゲームで共有し、ゲーム列とゲームごとの公開型で判別する。リバーシの既存JSON・API省略時の動作を維持し、将棋の参加者は色に代えて担当方向を持つ。将棋は最終状態・初期化情報・総イベント数・方向別の撃破数を保存し、棋譜の連番イベントは別行で保持する。終局と保存待ちの作成をDO内の同一トランザクションで確定し、DOの `shogi_archives` で保存待ちの局を保護し、D1の全イベントと対局本体・本人索引の保存が完了するまで保存元を消さない。D1の非公開 `shogi_match_uploads` と100イベントごとの `shogi_match_chunks` に分割してアップロードし、全チャンクを検証後に本体と本人索引を最後のbatchで公開する。保存途中は履歴・戦績・ランキングへ含めない。再送は同一対局IDとイベント番号で重複を防ぎ、保存済み結果を上書きしない。

本人の履歴と戦績は `game` で分離し、省略時は四人リバーシとする。ランキングはゲーム別のエンドポイントから取得する。アカウント画面の戦績・棋譜は独立したゲームSelectとゲーム別モードを持ち、取得結果もゲーム・モードごとに保持する。棋譜への遷移とマイページへの戻りではブラウザ履歴stateへ選択を渡し、URLと既存リンクを維持する。

将棋の保存棋譜は本人確認後に詳細と100件単位のイベントを取得し、エンジンで再生して保存された最終局面と照合する。ページ取得の中止・不整合・失敗を扱い、通常ルームの通信と参加資格には接続しない。盤面と持ち駒、棋譜・結果はオンライン将棋の表示部品を再利用し、本人の担当方向を下へ置く。マイページと共通ヘッダーは緑、将棋の保存棋譜とランキングは黄色のテーマを使う。
