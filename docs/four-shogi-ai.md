## Constraints

- 公開レベル `1 | 2` とLv1の一様ランダム選択を維持し、Lv2を強化する。
- 合法手、王手優先、三人攻撃禁止、同時脱落、順位、千日手、引分提案のルールと通信・保存形式を変更しない。
- 探索と実対局で状態遷移を共有し、高速経路と通常経路の結果一致を検証する。
- 入力状態を変更しない。同じ状態・探索予算なら同じ手を選ぶ。探索履歴を永続化しない。
- 次手番は毎回エンジンから取得する。探索キャッシュは三人攻撃、反復回数、順位など結果に影響する履歴を区別する。
- 探索を処理量で制限し、打切り時も合法手を返す。同期計算中の時計だけに依存しない。
- TypeScript/Bunと既存Cloudflare構成を使う。GPU、有料推論API、新規外部サービス、対局中の外部通信を追加しない。
- 本番データは公開APIを使う。本番D1直接アクセス、外部棋譜の大量取得、提供者への連絡は別途明示承認を得る。
- 調整用と最終評価用は棋譜単位で分離する。回転した同じ系列は同じ集合に置く。対戦の席順・序盤を変え、同一対局の反復を独立した証拠に数えない。
- 比較対象コミット、局面集合、seed、実行環境、測定対象コミットを記録する。基準を黙って下げず、未達時は原因・試した改善・残る選択肢を報告する。
- 長時間の棋力・性能測定は通常の `check` から分離し、ブラウザを起動する自動テストを追加しない。`check` の目標は180秒以内。
- CPU仕様の変更は該当仕様文書と同じコミットで更新する。mainへの直接push・force push、未承認のマージ・公開を行わない。

## 検証と未確認事項

測定は `bun run --cwd packages/four-shogi bench` から実行する。例は `--kind=performance --candidate=baseline --repeats=5 --output=/tmp/shogi-performance.json`、`--kind=matches --mode=singles --restricted=true --games=200 --max-plies=400 --output=/tmp/shogi-matches.json`。旧Lv2は固定コミットのソースを一時ディレクトリへ展開して実行し、測定終了後に削除する。結果にはコミット・未コミット変更の有無・Bun版・OS・アーキテクチャ・引数を記録する。性能局面集合にはSHA-256を付け、対戦の95%区間は開始系列を単位にしたbootstrapで求める。長時間測定を `check` へ組み込まない。

`--kind=tactics` は13系統を4方向・三人攻撃ON/OFFへ展開した104局面を測定する。回転した同じ系統を独立した104個の手筋とは扱わず、系統数と設定別の件数を併記する。既存回帰9系統72局面と追加検証4系統32局面を分離し、正解判定は捕獲対象、成り、実際の手番、詰み・応手などエンジンで確認する。マジックの取り返しが合法でも手番違いで実行できないことと、下家の全応手後に自手番が戻ることを固定局面で確認した。予備測定は104/104正解、重要問題の失敗0。最終コミットでの再測定は別途行う。

基盤の検証では、未終局・引分・勝利の集計、p95・最大時間、同じseedの合法な開始系列の再現を確認した。短い対戦は動作確認であり、受入基準の棋力測定ではない。

評価の調整は `--weights='{"kingRing":50,"undefended":0.8}'`、探索量の比較は `--max-work=2048` で行う。名前・値を検証し、指定しない重みは既定値を使い、引数と適用設定を結果へ残す。調整中の手筋確認は `--kind=tactics --split=regression` に限定する。対戦の調整用seedは1000台（シングルス）・2000台（ダブルス）、最終評価用は100000以降とする。候補を変えた場合は同じ調整用系列で旧候補と比較し、棋力・性能・重要問題を確認して採用を決める。最終評価局を調整へ使わない。序盤候補は現行エンジンで合法性を確認した中央歩の4手の系列だけで、同点時の優先に限定する。

段階5の調整用シングルスOFF 8局（2系列、席均等）では単独1位6局、引分2局、未終局0局だった。少数の調整用測定であり、受入基準の200局とは別に扱う。

オンラインは既存の公開CPU APIを通じて強化したLv2を利用する。4設定の飛車取りを実Workerの保存境界から選ばせ、選択中の盤面・revision・棋譜・千日手履歴が変化しないこと、次のAlarmで捕獲・持ち駒・revision・棋譜を1回だけ確定することを確認する。局ID・revision・手番違いの保存選択を破棄し、Lv2でも期限切れを着手しない。履歴1000件・10000件で読取り行数が増えないことと、ロールバック・次局の履歴分離も既存のWorkerテストで検証する。思考情報を通信・保存形式へ追加しない。

共有の着手確定処理を導入し、CPUが生成済みの合法候補を再検証せず進めるようにした。三人攻撃の禁止対象がない場合、公開着手は単手の通常合法性確認を使い、次手番の合法手有無は最初の1件で確定する。禁止対象がある場合は全通常候補による例外判定を維持する。4設定の全候補と攻撃・取り返し・反復履歴付き候補で、公開APIと共有経路の結果・入力不変を確認した。

提出前に `bun run check`、`bun run build`、`bun run --cwd apps/worker deploy:dry-run` をすべて成功させ、GitHub CI成功を別途確認する。PR提出後もコード・設定が変われば再実行する。

## シングルス専用AIの限定探索実験（#188）

この節はIssue #184の承認済みD01〜D05と#188に基づく新AIの内部実験です。上の2026-10-08の公開Lv2の測定・採用記録、固定基準 `913a09d`、当時の設定を変更しません。合法手/手番/勝敗は同じ正本で、三人攻撃ON/OFFを分けます。

#187の取込 `65380c8` を参照版とし、駒一覧の重複走査、実行内の不変状態キャッシュ、手順序、深さ/幅/延長、kingRing係数を比較します。初回プロファイルでは `pieces` の単一ホット区間が自己時間22.4%を占めました。盤面複製やキー生成も独立に測りましたが、今回は主要な駒走査と再計算へ改善を絞ります。キャッシュは履歴を省いた局面キーを作らず、同じ入力/枝の参照だけを共有します。

調整は旧regressionのシングルス7構図56展開と、新しい王手付き捕獲/逆王手/飛車損の3構図24展開。ON/OFFと4方向を別条件として記録し、回転した8展開を8個の独立な手筋とは数えません。旧validationと最終seed100000以降を調整へ使用せず、新しい対局/性能の開始seedは18800台です。これらは調整・smokeで、#197の最終評価と区別します。

予備比較では延長2手で候補一巡が完成せず即詰みを見落とすケースがあり、1手で重要回帰の失敗を解消できました。幅3は成りの見落としが増え、深さ6への上限縮小・前回の有望手順序・kingRing50では採用に足る改善を確認できませんでした。内部既定はMaxⁿ・延長1・キャッシュ256とし、残る失敗や同時間の対戦を記録して棋力の保証にはしません。
