# 0011 ゲーム契約の形

- 状態: 承認済み（2026-11-15）。[0004](0004-game-contract.md) の「契約の形はフェーズ 3 の冒頭で決めます」を具体化します。

## 状況

2026-11-15 の develop を読んで分かったことです。

- **登録表**: `apps/worker/src/rooms/gameProgress.ts` に、開始、着手、投了、CPU、終局、再戦待ちの登録表がすでにあります。ただ、各ゲームの進行クラス（300〜650 行）が次の仕事を 1 つのクラスで持っています。
  - 本人確認、古い局面の拒否、時計の期限、手番の確認
  - ルールの適用、公開する状態の整形
  - DO の保存（kv の CPU ジョブ、SQLite の反復局面と棋譜のイベント）
  - 外部 AI とのやり取り
- **`gameRoom.ts` の分岐**: ゲームの種類を判定する分岐がおよそ 120 か所あります（`isShogiRoom` 32、`isFourShogiRoom` 30、`isReversiRoom` 13 など）。
- **古い局面の拒否**: 将棋と五目並べは、局 ID と局面の版（`positionRevision`）を照合します。リバーシは照合しません。
- **CPU**: 全ゲームが DO の中で同期探索します。選んだ手を保存し、次の Alarm で期限を確かめてから適用します。外部 AI は、リバーシ、四人リバーシ、将棋、四人将棋が使います。通常リバーシだけは、GET や WebSocket の処理からも CPU 探索を行います。
- **ゲーム固有の操作**: 引分提案（将棋の 2 種類）、入玉宣言（将棋）、待機中の設定（四人将棋の三人攻撃禁止、五目並べの禁手）、使用戦型の記録（四人将棋）、脱落者の持ち駒の表示（四人将棋）があります。
- **レート**: Elo がリバーシと将棋、mu と sigma の方式（以下 skill）が四人リバーシと四人将棋です。五目並べの 2 種類はレートがなく、勝敗の数で順位を付けます。
- **棋譜**: 持ち方が 2 種類あります。
  - リバーシ、四人リバーシ、五目並べ、四人五目並べ: 1 手ごとに盤面全体を保存します（`replay.steps[].game`）。本番の四人五目並べの棋譜は、平均 157KB、最大 395KB です。
  - 将棋の 2 種類: 最初の局面とイベントだけを保存し、エンジンで再生して、保存した最終局面と照合します。四人将棋の最長の局は 3,343 イベントで 391KB です。
- **web の登録**: ゲームを 1 つ足すと、protocol、worker、web の登録表を 9 か所更新します（`docs/development.md` の「ゲームの必須登録と型の対応」）。

## 決定

### 置き場所

- 契約の型は `packages/game-contract` に置きます。Cloudflare にも zod にも依存しない、型と小さな補助関数だけのパッケージです。
- 各ゲームのパッケージ（`packages/shogi` など）が `definition` を書き出し、契約を実装します。ルールの中身（判定アルゴリズム）は変えません。
- web と共有する軽いカタログは、エンジンを含まない別の入口（`@tetraboard/<game>/catalog`）から書き出します。web のチャンクに別ゲームのエンジンが混ざらない、今の検査を保つためです。
- ゲームの一覧は 1 つの登録表（`satisfies Record<GameId, GameDefinition>`）にまとめ、ゲームの追加はパッケージ 1 つとこの登録 1 行で済むようにします。

### 契約の中身

`GameDefinition` は次の 5 つの部分でできています。どれも純粋な関数で、時刻、乱数、保存先は引数で受け取ります。

| 部分 | 中身 |
| --- | --- |
| カタログ | ゲーム ID、席の数（2 か 4）、席の名前（色や方向）、モード（シングルスとダブルス）、表示名、レートの方式（`elo`、`skill`、`none`）、待機中に変えられる設定とその既定値 |
| ルール | 最初の状態を作る、操作を適用する（着手のほか、引分提案や入玉宣言などそのゲームの操作の判別 union）、席を脱落させる、終局を判定して結果（順位、チーム、引分）を返す、手番の席を返す、公開する状態を作る |
| 局面の履歴 | 千日手のように過去の局面の数が要るゲームは、局面のキーを返します。数の保存と検索は対局ルームの文脈が持ち、検索の関数を引数で渡します。 |
| CPU | 同期探索で手を選ぶ（状態、レベル、乱数、履歴を受け取る）。外部 AI を使うゲームは、要求の作り方と応答の解釈を書き出します。最低 2 秒、ジョブの保存、Alarm での期限の再確認は、全ゲーム共通で対局ルームの文脈が持ちます。 |
| 棋譜 | 棋譜の最初の局面とイベントの型、イベント列を再生して最終状態を作る関数。対局ルームは受理したイベントを順に積み、終局時に棋譜の文脈へ渡します。 |

レートの計算は、レートの文脈が方式ごとに 1 つずつ持ちます。ゲームは方式を選ぶだけです。ダブルスのチームの組み方は、ルールの結果から渡します。

### 対局ルームの文脈が持つ共通の流れ

次の処理は全ゲーム共通にし、ゲームごとの分岐を持たせません。

1. 本人確認（トークン → 席）
2. 古い局面の拒否（局 ID と `positionRevision` の照合。全ゲームで行います）
3. 時計の期限と手番の確認
4. 契約のルールで操作を適用する
5. 確定（時計を進める、イベントを積む、終局を判定する、配信する）

投了、退室と切断による脱落、再戦の待機、CPU の予定、外部 AI のジョブもここに置きます。DO の殻は、保存、Alarm、WebSocket を受け持つだけにします。

### 互換の確かめ方

- 既存の棋譜のフィクスチャを、今の実装と契約の実装の両方で再生し、全ステップの状態と最終結果が一致することを確かめます。
- 四人リバーシと四人将棋の Rust の実装との一致の確認は続けます。

### 移す順序

1. `packages/game-contract` と登録表を作り、五目並べ（いちばん小さく、外部 AI がない）を試験的に移します。
2. 残りの 5 ゲームを 1 ゲーム 1 PR で移します。順序は、通常リバーシ、四人五目並べ、四人リバーシ、将棋、四人将棋の予定です。
3. `gameRoom.ts` からゲームの分岐を消します（ADR 0010 の殻の分割と合わせます）。

## 却下した案

- **進行クラスの基底クラスを作り、継承でそろえる。** 保存先と DO への依存が残り、Cloudflare なしでテストできません。
- **画面の描画も今回の契約に含める。** web はフェーズ 4 で SvelteKit に作り直すので、今決めても作り直しになります。カタログだけを先に固めます。
- **状態を `unknown` にし、実行時の検証だけで扱う。** ゲームと状態の取り違えを型で防げなくなります。

### 棋譜の形式

- 新しい対局の棋譜は、全ゲームで「最初の局面 + イベント」にそろえます。将棋の 2 種類と同じ形式です。棋譜は、本体 1 行とイベントのチャンクで保存します。
- 既存の将棋以外の約 385 局は、イベント形式へ変換します。変換の前に、イベント列を再生して、保存されている全ステップの盤面と最終結果が一致することを全局で確かめます。元の `record_json` は事前にバックアップします。
- 変換したら、1 手ごとに盤面全体を持つ形式を読む処理を消します。
- フェーズ 3 の深掘りで決めた「中身の形式を変えずにチャンクへ分ける」は、この変換に置き換えます。

### リバーシの局面の版と CPU

- リバーシと四人リバーシの着手の要求にも、局 ID と `positionRevision` を加えます。全ゲームで古い局面の応答を拒否します。
- 通常リバーシの CPU は、他のゲームと同じく Alarm だけで動かします。GET や WebSocket の処理からは探索しません。最低 2 秒の仕様は変えません。実装の前に、時計と GET の進行の契約を確かめます。

## 影響と未決

- 棋譜の変換で、本番の `matches` の `record_json` を書き換えます。変換の PR では、全局の照合の結果と、バックアップの場所を示してから、本番への適用の承認を得ます。
- リバーシの局面の版を加えると、開いたままの古い web のタブからの着手は拒否されます。拒否されたときに再読み込みを促す今の仕組みで足りるかを、実装時に確かめます。
- 外部 AI の要求と応答を契約へ移したときに、今の AI サービスとの互換が保てるかは未確認です。実装時に確かめます。
