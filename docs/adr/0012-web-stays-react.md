# 0012 web は React のまま、効果のある所を直す

- 状態: 承認済み（2026-11-20）。[0002](0002-web-and-api-workers.md) を置き換えます。

## 状況

0002 では、web を SvelteKit へ移し、公開ページを SSR にすると決めました。成功の基準は、公開ページの初期表示と SEO・OGP の改善、コード量の削減です。移行の前に基準値を測ることにしていました。

2026-11-20 に測った基準値です。

- 利用者の実測の Core Web Vitals（Cloudflare Web Analytics、2026-11-14〜11-20 の 7 日、ボットを除く）
  - LCP の P75 は、サイト全体で 980 ms、総合ロビーで 582 ms、ゲームのロビーで 366〜628 ms です。LCP が「良い」の割合は 95% です。
  - INP が「良い」の割合は 91%、CLS が「良い」の割合は 94% です。
  - LCP が「悪い」要素の多くは、ゲームのロビーの盤面の背景画像です。
- 初回に読み込む JS は、どの画面も同じ 11 ファイル（Brotli 328 KB、展開後 1,039 KB）です。画面は遅延読み込みになっていますが、共通の部分が大きな部品を取り込んでいます。
- web のコードは約 3.2 万行（342 ファイル）です。書き直す間は機能開発を凍結します。

利用者が感じる速さは、すでに良い水準です。書き直しで残る利点は、SEO とコード量の削減です。

## 決定

- web は React のままにし、SvelteKit へ移しません。
- Worker は 1 つのままにし、web と api を分けません。
- フェーズ 4 では、次の 3 つを行います。
  - 初回に読み込む JS を画面ごとに分けて減らします。数値の目標は、読み込みの中身を分析してから決めます。
  - 盤面の背景画像による LCP の遅れを直します。
  - ルームを作るときの通信の往復を減らします（0010 の C06 の web 側）。
- 成功の基準は次の 2 つです。
  - LCP の P75 を悪くしないこと。リリース後 7 日分を、サイト全体 980 ms、総合ロビー 582 ms と比べます。
  - JS の数値の目標を満たすこと。
- 検索向けの HTML や OGP が要るページは、今のロビーやルームの共有と同じく、Worker が HTML を返す方式で作ります。
- フェーズ 4 を終えたら、機能凍結を解きます。

## 却下した案

- **0002 のとおり SvelteKit へ移す。** 速さの改善はほとんど見込めません。SEO は Worker が HTML を返す方式でも得られます。全画面を書き直す間、機能凍結が続きます。
- **公開ページだけ SvelteKit にする。** React と Svelte が並び続け、保守の負担が増えます。

## 影響と未決

- [0001](0001-incremental-migration.md) にある「React と Svelte が並ぶ」状態は起きません。フェーズ 6 の掃除の対象は、旧コードと旧文書です。
- [0011](0011-game-contract.md) で画面の描画の契約を決めなかった理由は、web の作り直しでした。作り直しはなくなったので、要るときに改めて決めます。
- 検索向けのページ（大会、ルール、棋譜）と OGP の追加は、利用者に見える仕様の追加です。機能凍結を解いた後、1 件ずつ仕様を承認してから行います。
