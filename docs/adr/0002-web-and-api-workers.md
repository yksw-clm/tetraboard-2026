# 0002 web と api を別の Worker にし、同一オリジンに載せる

- 状態: 承認済み（2026-11-14）。詳細はフェーズ 4 の冒頭で決めます。

## 状況

現在は 1 つの Worker が、Web の静的ファイル、管理画面、API、WebSocket をすべて同一オリジンで配信しています。実行時の SSR はなく、総合ロビーと 6 つのゲーム別ロビーだけ、ビルド時に静的な HTML を生成しています。その HTML は React が起動すると置き換えられ、hydrate はしていません。

web を SvelteKit へ移し、公開ページを SSR にします。

## 決定

- web（SvelteKit の SSR）と api（Hono と Durable Objects）を別の Worker にします。
- どちらも `tetraboard.net` の同一オリジンに載せます。`/api/*` と WebSocket は api へ、それ以外は web へ振り分けます。
- SSR から api への呼び出しは Service Binding を使います。
- SSR の対象は公開ページ（トップ、ロビー、ルール、大会、マイページ、棋譜閲覧など）です。対局画面は枠だけ SSR し、盤面と通信はクライアントで描画します。
- ページ群ごとに切り替えます。順番は、静的な公開ページ、ロビー、アカウントと棋譜、大会、対局画面です。移した URL から順に web Worker が配信します。
- 成功の基準は、公開ページの初期表示と SEO・OGP の改善、コード量の削減です。移行前に LCP と JS サイズを測り、比べる基準にします。

## 却下した案

- **1 つの Worker に SvelteKit と Durable Objects を同居させる。** web だけの変更でも Worker 全体のテストとデプロイが必要になります。
- **web と api を別オリジンにする。** Cookie と認証の設定を変える必要があり、CORS の扱いも増えます。
- **全画面を作り終えてから一度に切り替える。** 0001 の方針と合いません。

## 影響と未決

- 移行中は、React 側のページと Svelte 側のページの行き来がページ全体の再読み込みになります。
- SSR は対局中の操作感を改善しません。盤面は DOM 描画で、CPU の思考はすべてサーバー側にあります。
- **未確認**: SvelteKit の Cloudflare 向けアダプタの現行仕様と、同一オリジンで 2 つの Worker に振り分ける設定方法。フェーズ 4 の冒頭で公式文書を確かめます。
