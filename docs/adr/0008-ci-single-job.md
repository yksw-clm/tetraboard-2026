# 0008 CI は 1 つのジョブにまとめ、AI のジョブだけを差分があるときに分ける

- 状態: 承認済み（2026-11-14）。[0007](0007-ci-and-tests.md) の「ワークスペース別のジョブに分けて並列で走らせる」と「ローカルの `bun run check` で 90 秒以内」を置き換えます。

## 状況

0007 では、CI をワークスペース別のジョブに分けて並列に走らせると決めました。その後、次のことが分かりました。

- GitHub Actions は、ジョブごとに所要時間を分単位に切り上げて課金します。ジョブを分けると、ジョブごとの準備（checkout、mise、`bun install`、約 30〜40 秒）が重なり、利用時間の合計が増えます。
- 2026-10-19 から 11-14 の 26 日間で、ジョブの合計はおよそ 2,240 分でした（ジョブごとに分を切り上げて足した概算）。非公開リポジトリの無料枠を超えている可能性があります。
- ローカルの `bun run check` の残りの大部分は Worker の統合テストで、これを縮めるのはフェーズ 3 のバックエンド再設計です。

## 決定

- 通常の PR では、ジョブを 1 つ（`checks`）にまとめます。中のテストは、CPU 数と 4 の小さいほうの並列数で走らせます。
- AI のテスト、AI コンテナのイメージ検証、AI の dry-run は `ai` ジョブに分け、AI のパスに差分があるときと main への push のときだけ走らせます。
- 目標は、待ち時間（`checks` ジョブ）が 4 分以内、PR 1 回あたりの利用時間が以前より少ないこと、手元の `bun run check` が 150 秒以内です。手元で 90 秒以内はフェーズ 3 の完了条件にします。
- `checks` が 4 分を超え続けたら、Worker テストだけを 2 つ目のジョブに出します。

## 却下した案

- **ワークスペース別のジョブに分ける（0007 の案）。** 待ち時間は少し短くなりますが、PR 1 回の利用時間が約 2 倍になります。

## 影響と未決

フェーズ 1 の変更ごとの `checks` ジョブの所要時間（GitHub Actions の実測）は次のとおりです。

| 時点 | `checks` | 内訳の主なもの |
| --- | ---: | --- |
| 変更前の Full CI（直近 9 件の中央値） | 約 590 秒 | `packages/ai` のテストと本番 AI の dry-run を含む。別に AI イメージの検証ジョブが約 200 秒 |
| AI を外した後（#367） | 350 秒 | 開発向けビルドの工程が約 3 分。開発 AI の dry-run が Docker イメージをビルドしていた |
| 並列数 4（#368） | 379 秒 | 並列数の効果は誤差の範囲（検証の工程 151 秒 → 146 秒） |
| 開発 AI の dry-run を `ai` ジョブへ移した後（#369） | 200 秒 | 目標の 4 分以内 |

- 並列数を 4 に上げた効果は、ランナー上ではほとんど見られませんでした。テストの所要時間の多くは Worker の統合テストの 2 プロセスが占めていて、残りの 2 枠が空いても全体は短くならないためです。
- AI に触れる PR と main への push では、`ai` ジョブが `checks` の後に直列で走るため、待ち時間は約 8〜12 分になります。
- Actions の請求額は、権限がなく確かめていません（未確認）。
