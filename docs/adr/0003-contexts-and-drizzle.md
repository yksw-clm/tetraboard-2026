# 0003 contexts による軽い DDD と drizzle を採用する

- 状態: 承認済み（2026-11-14）。詳細はフェーズ 3 の冒頭で決めます。

## 状況

worker は、ルート、保存処理、Durable Object の 3 種類でできていて、ドメインの層がありません。`apps/worker/src/rooms/gameRoom.ts` は 5,282 行あり、席、時計、WebSocket、索引の同期、棋譜の保存、大会、登録フロー、退会の同期を 1 つのクラスが持っています。

D1 には約 102 のテーブルと 141 のトリガーがあり、生 SQL の呼び出しが 550 箇所あります。整合性を守る処理の多くがトリガーにあります。レート変更や棋譜のテーブルはゲームごとに分かれています。

ロジックの大半を workerd 上の統合テストで確かめているため、テストに時間がかかります。

## 決定

- `packages/contexts/<文脈>/` に、domain（Cloudflare に依存しない純粋な TypeScript）と use-cases を置きます。保存先は、use-cases の側で定義したインターフェース越しに渡します。
- 文脈の候補は、対局ルーム、マッチング、大会、アカウント、レート、棋譜、コミュニティ（チャット、通報、お知らせ）、プライバシーです。境界はフェーズ 3 の冒頭で確定します。
- Durable Object は、純粋な状態遷移の関数を載せる薄い殻にします。時計、通信、保存は殻の側が持ちます。
- drizzle を採用します。同じ D1 を使い続け、スキーマを段階的に変えます。既存の 46 本の migration は、drizzle へ移る時点で 1 本の基準にまとめます。
- 整合性を守るトリガー（退会、ゲスト統合、1 アカウント 1 席）は use-cases へ順に移します。UNIQUE などの制約は DB に残します。
- スキーマ全体の目標形を、フェーズ 3 の冒頭で 1 本の設計文書にまとめます。見直すのは、ゲーム別に分かれたテーブルの統合、棋譜を 1 つの JSON で持つ形、ゲストと登録フローのテーブル、無期限に増えるデータの保持ルール、命名の統一です。

## 却下した案

- **イベントソーシング、全テーブルに一律でリポジトリを用意する形。** 1 人で保守する規模に対して層が増えすぎます。
- **層を足さず、ルートと保存処理の 2 層のまま整理する。** `gameRoom.ts` を Cloudflare から切り離してテストする場所がなくなります。
- **新しい D1 を作って一括で移行する。** 0001 の方針と合いません。

## 影響と未決

- 保持期間を変えることは、利用者向けの仕様変更です。設計文書の中で、項目ごとに開発者の承認を得ます。
- トリガーを移している間は、同じ整合性のルールが DB とコードの両方にある期間ができます。移し終えたトリガーは同じ変更で消します。
