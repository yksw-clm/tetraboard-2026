# 0015 掲示板の投稿の詳細ページを、Worker が D1 から生成して検索に載せる

- 状態: 承認済み（2026-11-26）

## 状況

掲示板では、各ゲームのタイムラインに登録者が投稿し、投稿ごとに詳細ページ（全文、添付した棋譜の局面、返信）を持ちます。目的の 1 つは、詳細ページを検索に載せて流入を増やすことです。

検索向けの HTML は、いま 2 通りの方法で返しています。

- ロビー、ルール、サイトの利用ガイドは、ビルド時に HTML を生成します。
- 大会一覧と公開済みの大会詳細は、要求ごとに Worker が D1 を読み、title、description、canonical、OGP、JSON-LD、本文を `app.html` に差し込みます。サイトマップにも、Worker が公開済みの大会を足します（TB-121）。この方式には ADR がありません。

投稿は大会と違い、利用者が書き、件数に上限がなく、無期限に残ります。大会ページの方式をそのまま広げると、次のことが決まっていません。

- 利用者の投稿を検索に載せてよいか、どの投稿を載せるか。
- ページ数が増えたときのサイトマップの分け方。
- 投稿の削除と退会を、検索向けの HTML とサイトマップにどう反映するか。

Google の公式文書（Search Central、2026-11-26 に確認）では、次のとおりです。

- フォーラムやコメント欄を持つこと自体はポリシー違反ではありません。ただし、利用者が投稿したスパムが残っていると、順位が下がったり表示されなくなったりすることがあります（スパムに関するポリシー）。
- 利用者の投稿には `DiscussionForumPosting` を使います。必須は `author.name`、`datePublished`、`text`・`image`・`video` のどれかで、投稿の全文を含めます（Discussion forum の構造化データ）。
- 利用者の投稿内のリンクには `rel="ugc"` を推奨しています（外部リンクの指定）。
- サイトマップ 1 ファイルは 50,000 URL、非圧縮で 50MB までです。超えるときは分割し、サイトマップ インデックスでまとめられます。`lastmod` は、正確な場合だけ使われます。`priority` と `changefreq` は使われません（サイトマップの作成、大きなサイトマップの管理）。
- 「内容の薄い投稿を noindex にする」という推奨は、公式文書にはありません。
- 500 と 503 を返すと、クロールの頻度が一時的に下がります。すでに index された URL は残りますが、エラーを返し続けると、いずれ index から外れます（HTTP ステータス コードの扱い）。

D1 は 1 データベース 10GB まで（Workers Paid）で、1 つのデータベースはクエリを 1 件ずつ処理します（Cloudflare D1 の Limits、2026-11-26 に確認）。

## 決定

- 投稿の詳細ページ `/posts/:id` は、大会詳細と同じ方式で返します。要求ごとに Worker が D1 から投稿と返信を読み、`app.html` に title、description、canonical、OGP、robots、JSON-LD、本文を差し込みます。画面の起動後は React の画面に置き換えます。
- 読み取りが期限内に終わらない、または失敗したときは、大会ページと違って HTTP 503 で画面の HTML を返し、画面で再試行を案内します。大会ページのように 200 と `noindex` を返すと、障害の間にクロールされた投稿が検索結果から外れるおそれがあるためです。
- 詳細ページで最初に読む返信は 50 件までにします。続きは画面から 50 件ずつ取得します。返信が増えても、1 回の表示で読む量と HTML の大きさが増え続けないようにするためです。初期 HTML と JSON-LD に入れる返信も、この 50 件だけです。
- JSON-LD は `DiscussionForumPosting` を 1 件入れ、投稿の全文、投稿者の現在の名前、投稿日時を含めます。返信は `comment` に入れます。削除された投稿と返信の本文は、HTML にも JSON-LD にも入れません。
- 投稿が公開されているかどうか（存在する、削除された枠だけ残る、見つからない）と index するかどうかは、Worker の 1 か所で決め、公開の API、詳細ページの初期 HTML、サイトマップが同じ判定を使います。削除された投稿は、返信がなければ 404、返信があれば「削除された投稿」の枠と返信を `noindex` で返します。
- index するのは、本番で、削除されておらず、仕様書（`docs/specs/board.md`）の index の条件を満たす投稿だけです。それ以外は HTML と `X-Robots-Tag` で `noindex, follow` にします。条件の中身は利用者に見える振る舞いなので、仕様書で決めます（2026-11-26 に開発者が、投稿から 24 時間が過ぎ、返信が 1 件以上または本文が 50 字以上、と承認）。
- 投稿の直後は運営が消せるように、一定の時間を置いてから index します。いいねの数は、投稿者が別のアカウントで増やせるので条件に使いません。
- タイムライン `/games/:gameId/posts` は `noindex, follow` にします。新しい投稿が来るたびに内容が入れ替わり、同じ投稿が詳細ページと二重に載るためです。詳細ページは、サイトマップとタイムラインのリンクからたどれます。
- 投稿のサイトマップは、ロビーや大会を載せている既存の `/sitemap.xml` とは別のファイルにし、robots.txt から参照します。載せるのは index する投稿だけです。`lastmod` は、投稿、返信、削除の最後の日時にします。いいねでは変えません。50,000 URL に近づいたら、ファイルを分けてサイトマップ インデックスでまとめます。最初は分けません。
- 投稿の本文に書けるリンクは、TetraBoard の中の棋譜、大会、ルームだけです。外部へのリンクがないので、`rel` は付けません。外部のリンクを許すときは `rel="ugc"` を付けます。
- 検索向けの HTML は `no-store` で返します。削除、退会、運営の削除を、次の要求からすぐ反映するためです。

## 却下した案

- **詳細ページの HTML をビルド時に生成する。** 投稿のたびにデプロイが要り、削除をすぐ反映できません。
- **詳細ページを検索に載せない（すべて `noindex`）。** 一番安全ですが、検索からの流入という目的の 1 つを捨てることになります。スパムは通報、運営の削除、index までの待ち時間で抑えます。
- **タイムラインを index する。** 内容が入れ替わり続け、詳細ページと同じ本文が重なります。
- **投稿をすべて index し、運営の削除だけで質を保つ。** 一言だけの投稿が大量に載ると、サイト全体の評価に響くおそれがあります。運営の人手は限られています。
- **投稿を既存の `/sitemap.xml` に混ぜる。** 件数が増えると、固定のページと大会を同じファイルで分割することになり、`/sitemap.xml` の作りを変える必要があります。
- **投稿ごとに OGP 画像を生成する。** 公開棋譜と同じく、ゲームごとの既存画像を使います。生成と保存の仕組みを増やしません。

## 影響と未決

- Worker が要求ごとに D1 を読むページが、大会の数から投稿の数へ増えます。1 回の表示で読むのは投稿 1 件と、返信 50 件までです。クローラーの要求も同じ D1 に来ますが、1 件 1ms 程度のクエリなら 1 秒に数百件は処理できます。実際の負荷は、公開後に Cloudflare のダッシュボードで確かめます。
- 投稿は 1 件 3KB 以下で、1 日 100 件でも 1 年で 110MB ほどです。D1 の 10GB の上限には当面届きません。
- 削除された投稿の詳細ページを、Google がいつ検索結果から外すかは Google が決めます。こちらは `noindex` とサイトマップからの削除までを行います。
- 大会ページの方式には ADR がありませんでした。この ADR が、Worker が D1 から検索向けの HTML を作る方式の最初の記録です。
