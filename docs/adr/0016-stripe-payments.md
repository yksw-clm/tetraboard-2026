# 0016 決済に Stripe を採用し、決済のための情報の取り扱いを計測と分けて定める

- 状態: 承認済み（2026-11-28）

## 状況

2026-11-23 の収益化計画で、最初の売上を「TetraBoard サポーター」（月 480 円）で取ると決めました。課金できるのは Google か Discord と連携したアカウントだけで、ゲストは記録を引き継いで連携してから決済に進みます。通常の解約はいつでもでき、期間の終わりまで有効で、日割りの返金はしません。退会したときは課金を自動で止めます。勝敗やレートに影響する課金と、対局画面の広告は入れません。

いまのプライバシーの方針は次のとおりです（[docs/specs/privacy.md](../specs/privacy.md) と公開文言 `packages/protocol/src/privacy.ts`、版 2026-11-26 を確認）。

- 「処理と保存は運営者と委託先 Cloudflare で行う」と約束しているのは、利用計測についてです。計測情報を広告に使わず、販売せず、広告・外部解析サービスへ提供しません。
- 外部サービスの役割として、認証に Google・Discord、配信とデータ・画像の保存と計測に Cloudflare を挙げ、日本国外で取り扱われる場合があると説明しています。決済の提供者はありません。

決済を入れると、決済という新しい目的で、新しい提供者に情報が渡ります。計測の約束を広げたり崩したりせずに、決済の取り扱いを別に定める必要があります。

公式文書で確かめたこと（いずれも 2026-11-28 に確認）:

- **手数料。** 国内のカード決済は成功ごとに 3.6%、通貨換算が必要な場合は +2%。初期費用と月額料金はありません。3D セキュアは追加手数料なしです。返金の手数料はかかりませんが、元の決済の手数料は戻りません。不審請求の申し立ては 1 件 1,500 円です（[料金](https://stripe.com/jp/pricing)）。Billing の従量課金は Billing の取引額の 0.7% です。顧客ポータルは、カスタムドメインを使う場合だけ月額 $10 です（[Billing の料金](https://stripe.com/jp/billing/pricing)）。0.7% がカードの 3.6% に重ねてかかると読めますが、合算の例は料金ページにありません。重ねてかかるとすると、480 円の決済 1 件あたり約 21 円（4.3%）です。
- **日本での要件。** 開業届の有無を問わず、個人事業主として登録できます。本人確認には氏名、生年月日、住所、電話番号と本人確認書類が要ります。特定商取引法に基づく表示が必要で、表示がないことは審査に落ちる主な理由に挙がっています。日本では 3D セキュア 2.0 が自動で適用されます。審査は通常 2〜3 営業日です。本番環境の審査中でもテストできます（[日本のユーザー向けガイド](https://support.stripe.com/questions/getting-started-with-stripe-a-guide-for-users-in-japan?locale=ja-JP)）。TB-192 で、開業届を待たずに Stripe の準備を進めることは決まっています。
- **3D セキュアの義務化。** 2024-03-15 改訂の「クレジットカード・セキュリティガイドライン」により、日本でオンライン販売する事業者は 2025-03 末までに 3D セキュアを有効にする必要があります。Checkout は対応の変更が不要な方式として挙がっています。サブスクリプションでは、カードの登録時か初回の決済で 3D セキュアを済ませれば、以後の継続の決済は免除されうるとされています。義務化の規則を試す専用の環境はなく、テスト用のカードで確かめます（[日本の 3DS 義務化](https://support.stripe.com/questions/3ds-mandate-in-japan?locale=ja-JP)、ページの最終更新は 2025-06-25）。
- **サンドボックス。** 本番から分離されたテスト環境で、サンドボックスの決済はカードネットワークで処理されません（[サンドボックス](https://docs.stripe.com/sandboxes)）。
- **Stripe での保持。** Stripe は、法令の遵守、不正対策、会計などのために、取引の後も個人情報を保持しうると説明しています（[Stripe のプライバシーポリシー](https://stripe.com/privacy)）。
- **Workers からの呼び出し。** stripe-node は `Stripe.createFetchHttpClient()` で fetch を使い、Webhook の署名は `Stripe.createSubtleCryptoProvider()` と `constructEventAsync` で Web Crypto を使って検証します（[Cloudflare のブログ](https://blog.cloudflare.com/announcing-stripe-support-in-workers/)、2021-11-19 公開、2026-07-15 更新）。
- **Webhook。** 検証には `Stripe-Signature` ヘッダー、変更していない生の本文、エンドポイントごとの秘密が要ります。ライブラリの既定では、5 分より古い署名を拒みます。同じイベントが複数回届くことがあり、処理したイベント ID を記録して二重に処理しないよう勧めています。配信の順序は保証されません。本番では、指数バックオフで最長 3 日間再送します。サンドボックスでは数時間で 3 回です。時間のかかる処理の前に 2xx を返すよう勧めています（[Webhook](https://docs.stripe.com/webhooks)）。
- **Checkout の完了。** 顧客が戻り先のページを訪れるとは限らないため、戻り先だけを契機に提供してはいけません。サブスクリプションでは Webhook が必要で、同じ Checkout Session について処理が複数回、同時に呼ばれることもあります（[フルフィルメント](https://docs.stripe.com/checkout/fulfillment)）。
- **解約。** API の既定は即時の解約です。`cancel_at_period_end` を `true` にすると、現在の請求期間の終わりに解約されます（[サブスクリプションのキャンセル](https://docs.stripe.com/billing/subscriptions/cancel)）。
- **Checkout が集める情報。** `customer_email` を渡さなければ、Checkout が顧客にメールアドレスを入力させます。請求先住所の既定は「必要な場合だけ集める」です。`client_reference_id`（200 文字まで）は、自分のシステムと照合するための文字列です（[Checkout Session の作成](https://docs.stripe.com/api/checkout/sessions/create)）。
- **顧客ポータル。** Stripe がホストするページで、顧客が支払い方法の更新、サブスクリプションの即時または期間末の解約、請求書の表示を行えます。名前・メール・請求先住所の編集は既定でオンです。iframe では表示できません（[顧客管理](https://docs.stripe.com/customer-management)、[ポータルの設定](https://docs.stripe.com/customer-management/configure-portal)）。

## 決定

### Stripe を直接使う

サポーターの決済は Stripe の Checkout（サブスクリプションのモード）と Billing で行い、課金の状態は Webhook でサーバーに反映します。カード情報の入力は Stripe がホストする Checkout の画面で行い、TetraBoard のサーバーと画面はカード番号を受け取りません。開発環境は Stripe のサンドボックスで動かします。サンドボックスは本番の審査と別で、サンドボックスで動いても本番で受け付けられることにはなりません。

理由は、サポーターが「アカウントに結びつき、期間で始まり、期間末で終わり、退会で止まる」会員だからです。開始、更新、解約の予約、期間末の終了、退会による停止を、TetraBoard のサーバーが Stripe の API と Webhook で直接扱えます。

### 計測と決済を分けて扱う

- 利用計測の約束は変えません。計測は引き続き Cloudflare の中で完結させ、計測情報を Stripe に送りません。
- 決済は、新しい目的（サポーターの決済と会員の状態の管理）として、決済の提供者 Stripe の役割をポリシーに足す案にします。文言と法的な整理は TB-191 で決めます。
- 外部の広告は入れません。

### Stripe に渡す情報を絞る

TetraBoard から Stripe に渡すのは、次のものだけにする案です。

- 支払い専用の不透明な相関子。アカウントごとに乱数で作り、D1 で内部アカウント ID と対応づけます。Checkout Session の `client_reference_id` とサブスクリプションの metadata に入れます。内部アカウント ID、公開 ID、メールアドレスは使いません。Stripe 側の記録だけでは TetraBoard の公開プロフィールにたどり着けないようにするためです。
- 価格（月 480 円のサポーター）と、戻り先の URL。
- 解約、退会による停止、照合のための、Stripe の Customer ID とサブスクリプション ID を使った API の呼び出し。

次のものは Stripe に送りません。棋譜、戦績、レート、バッジ、大会の成績、公開プロフィール、OAuth のメール・識別子・トークン、計測データ。

メールアドレスも `customer_email` で渡しません。利用者は Checkout で自分で入力します。連携済みのメールを渡せば入力の手間は減りますが、OAuth で取得したメールを本人確認以外の目的で外部に渡すことになり、ポリシーの「Google から取得した情報は説明した用途に限定する」と衝突するためです。

### Stripe が利用者から直接集める情報

Checkout と Stripe の処理の中で、Stripe が利用者から直接集めます。

- カード情報（番号、有効期限、セキュリティコード）
- 領収と連絡のためのメールアドレス
- 必要な場合の名前と請求先住所
- 3D セキュアの認証のための情報（カード発行会社とやりとりされます）
- 不正対策のための端末と通信の情報（Stripe 自身の方針で集めます。項目は**未確認**）

カード番号とセキュリティコードは、TetraBoard のサーバーにも画面にも届きません。メールアドレス、名前、請求先住所、カードのブランドや下 4 桁は、Webhook や API の応答に含まれて TetraBoard のサーバーに届きえます。届いても、次の節に挙げるもの以外は保存せず、ログにも出しません。

### TetraBoard が Stripe から受け取って保持する情報

会員の状態を出すのに必要なものだけを保持する案です。

- 相関子と内部アカウント ID の対応
- Stripe の Customer ID とサブスクリプション ID
- サブスクリプションの状態、現在の期間の終わり、期間末の解約の予約の有無
- 請求書の支払い結果で確かめた支払い済みの期限（保存するか、そのつど Stripe から出し直すかは TB-193 で決めます）
- 処理済みの Webhook のイベント ID（重複を防ぐため）
- 発行済みの Checkout Session の ID と、作成を始めたが結果がまだ分からない Checkout の記録（1 アカウント 1 契約の維持と、退会との照合のため）

表とその列、保存期間は TB-193 で決めます。

### 会員の有効化は Webhook とサーバーでの照合で行う

Checkout の戻り先のページを開いたことは、会員を有効にする根拠にしません。戻り先は、決済を終えても閉じられて開かれないことがあり、逆に URL を知っていれば決済せずに開けるからです。会員の状態は、署名を検証した Webhook を受けたときに、サーバーが Stripe の API から最新のサブスクリプションを取得して決めます。戻り先のページは「処理中」を表示し、状態をサーバーに問い合わせるだけにします。

課金できるサポーターの契約は、1 つのアカウントに同時に 1 件までとします。別のタブで申し込んだり、応答が途切れてやり直したりすると、同じアカウントで Checkout Session がいくつも作られ、それぞれの完了で別の契約が成立しえます。`client_reference_id` は照合のための値で、契約を 1 件に限りません。Webhook の重複を除いても、月額の二重の請求は防げません。重複した契約を後から止めても、それぞれの初回の 480 円はすでに確定しえます。解約と返金は Stripe では別の操作です。2 件目の決済を成立の前に防ぐか、成立した後に余分な決済を特定して返金まで行うかを、TB-193 の受け入れ条件にします。方式（発行済みの Session の再利用や失効など）は TB-193 で決めます。返金で解決する場合は、利用者に見える振る舞いなので開発者の承認を得ます。

会員の状態を更新できるのは、そのアカウントの現在の契約だけです。期間末に終了した利用者が同じアカウントで再び加入した後に、古い契約の解約の通知が遅れて届くと、その古い契約を取り直しても状態は解約済みです。それでアカウントの会員の状態を上書きすると、新しい契約の特典が消えてしまいます。再加入の後に古い契約の通知が届く場合も、試験に含めます。

特典の期限は、契約の状態と現在の請求期間だけから出しません。請求書の支払い結果で確かめた、支払い済みの期限から出します。更新の請求に失敗しても契約の状態が有効のまま残る場合があり、状態と請求期間だけを見ると、未払いの期間を支払い済みとして扱ってしまうからです（Stripe の詳しい挙動は**未確認**）。猶予の期間は TB-193 で決めます。

Webhook の扱いは次のとおりにする案です。

- 署名を検証できない要求は捨てます。検証には変更前の生の本文を使います。
- 処理済みのイベント ID は記録し、同じイベントは二度処理しません。
- 届いた順にイベントの中身を当てはめません。順序が保証されないため、たとえば「更新」より後に古い「作成」が届いても、状態が巻き戻らないようにするためです。イベントは「このサブスクリプションを照合する」きっかけとして扱い、Stripe の API から現在の状態を取り直して反映します。
- 取り直すだけでは足りません。同じサブスクリプションの照合が並行して走ると、先に取得した古い結果が後から書き込まれて勝つことがあります。守る不変条件は「保存した状態は、すでに保存した状態より古い Stripe の状態で上書きされない」ことです。サブスクリプション単位で直列にするか、条件付きの更新にするかなどの方式は TB-193 で決め、並行と順不同の到着で巻き戻らないことを試験で確かめます。
- 2xx を返すのは、照合を終えたか、照合すべきことを受け付けて永続化した後です。永続化する前に無条件で 2xx を返すと、その後に失敗しても Stripe は再送せず、イベントが失われます。時間のかかる照合は、受付を永続化してから後で行ってかまいません。その場合、2xx を返した後に Stripe の API の障害などで照合に失敗しても、Stripe は再送しません。受け付けた照合は成功するまで再試行するか、運営者が失敗したものを再実行できるようにします。TetraBoard 側が落ちていても、本番では最長 3 日間再送されます。
- Webhook の設定の誤りなどで再送の期限を過ぎると、決済は成功しているのに会員が有効にならず、戻り先は「処理中」のままになります。再送の期限を過ぎても復旧できる経路（未配信のイベントの再処理や、Stripe の契約の一覧との照合など）を、公開の前に用意する案にします。定期の照合にするか、運営者が手で起動するかは TB-193 で決めます。
- D1 をバックアップから戻すと、復元地点より後に結んだ契約の、相関子と内部アカウント ID の対応が消えます。乱数の相関子からは契約者を割り出せず、Webhook を再送させても会員の状態とアプリからの解約を戻せません。既存の障害復元の手順（[runbooks/privacy.md](../runbooks/privacy.md)）が削除台帳を先に確保するのと同じく、復元の前に課金の対応表を確保して戻すことを、TB-193 の復元の要件にします。障害で復元元の D1 を読めない場合や、復元地点より後に作られたアカウントで対応表を戻しても参照先がない場合もあります。そのため、復元元に頼らずに対応を回復できること、参照先のない契約を公開の再開前に照合し、解約できないまま請求が続かないようにすることも要件にします。参照先のある契約も、すでに 2xx を返した Webhook は再送されないので、公開の再開前に Stripe と突き合わせて現在の契約の状態を戻します。戻さないと、支払っている会員が特典や解約の手段を失ったり、申し込み直して二重に請求されたりします。
- 退会したアカウントに対応するイベントは、会員を有効にしません。解約の処理だけを進めます。

### 解約と退会

- 通常の解約は、期間末の解約（`cancel_at_period_end`）にします。支払い済みの期間の終わりまで特典は有効で、日割りの返金はしません。これは収益化計画の方針どおりです。
- 解約の予定日と特典の期限は分けます。更新の支払いに失敗した後に解約した場合、`cancel_at_period_end` が指すのは現在の請求期間の末日で、支払い済みの期限ではありません。未払いの期間の特典は、承認された支払い失敗の扱いに従います。この ADR では決めません。
- 退会では、既存の退会の処理（[プライバシーの入口](../development.md#プライバシーの入口)）と同じ形にする案です。受付の D1 batch で「課金の停止」を退会の処理の対象に加えます。退会の処理は受付の直後にも動くので、課金の停止もそこで試み、毎時の退会の処理は失敗したときの再試行に使います。
- Stripe の障害で解約が失敗しても、退会の受付とアプリ内の利用停止は巻き戻しません。外部の連携解除の失敗で利用停止を巻き戻さない、いまの方針と同じです。
- 退会と Checkout の進行が重なる場合は、2 つに分けて扱います。退会の受付の後は、新しい Checkout Session を作りません。退会の受付より前に作った Checkout Session がその後に完了して契約が成立した場合は、会員を有効にせず、退会の処理と同じ経路で課金を止めます。Webhook が退会したアカウントの相関子を指していれば、この扱いになります。
- そのため、課金に関わる退会の処理を完了とする条件は、既存の契約を止めたことだけにしません。発行済みの Checkout Session を失効させるか結果を照合し、競合で成立した契約も止めたことを含めます。退会の前に Stripe へ送った作成の要求が退会の受付の後に成功すると、退会の処理が調べた時点ではその Session の ID がまだありません。退会と画像のアップロードの競合（[development.md](../development.md#プライバシーの入口)）と同じく、Stripe を呼ぶ前に進行中の作成を D1 に記録し、結果が分からない作成も照合するまで、課金の停止を完了にしません。それまでは、相関子、サブスクリプション ID、発行済みの Checkout Session の ID といった照合に要る最小限の識別子を、退会の処理の中で非公開に保持します。相関子を先に消すと、後から完了した Checkout や遅れて届いた Webhook を退会者に結びつけられず、課金を止められないからです。具体的な保持の期限は TB-191 と TB-193 で決めます。
- Stripe が正常でも、退会の直後に更新日を迎える契約では、解約が届く前に更新の課金が確定しえます。障害が長引いて更新日を過ぎた場合も同じです。どちらも、退会受付の後に課金が 1 回発生しえます。退会の処理が Session を失効させる前に Checkout が完了した場合も、特典は一度も有効にならないのに、初回の 480 円は確定しえます。契約を止めても、確定した決済は取り消されません。これらの決済を返金するか、どう案内するか、退会では即時に解約するか期間末に解約するかは、利用者に見える振る舞いなので、TB-191 と TB-193 で開発者の承認を得て決めます。

### 顧客ポータルは利用候補にとどめる

Stripe の顧客ポータルは、利用候補として挙げます。理由は次のとおりです。

- カードの更新、期間末の解約、請求書の表示を、カード情報に触れずに Stripe のページで済ませられます。
- 解約や支払い方法の変更の画面を TetraBoard で作らずに済みます。
- カスタムドメインを使わなければ追加費用はかかりません。

一方で、名前・メール・請求先住所の編集が既定でオンになっていることや、iframe で表示できないことは、使う場合の設定と画面の流れに影響します。ポータルを使うかどうか、課金状態をどの表に持つか、支払いに失敗したときの扱い（猶予の期間、特典を止める時期）は TB-193 の未決のままで、この ADR では決めません。

## 却下した案

- **Ko-fi。** 支払いの時の Webhook はありますが、会員の終了は通知の対象外です（[Ko-fi のヘルプ](https://help.ko-fi.com/hc/en-us/articles/360004162298-Does-Ko-fi-have-an-API-or-webhook)）。期間末の終了と、退会による課金の停止を TetraBoard から確実に扱えないため、アカウントに結びつく会員の仕組みには向きません。支払いの通知を相関子と結びつけること自体ができないとは言いません。
- **pixivFANBOX。** 外部サービスが支援者の状態を受け取る公式の API や Webhook を、公式の文書で確認できませんでした（**未確認**。2026-11-28 にヘルプセンターの取得を拒否されました）。確認できない限り、会員の開始、終了、退会による停止を TetraBoard と結びつける設計を立てられません。
- **外部の広告。** 広告の配信は、広告事業者に閲覧の情報を渡し、他サービスをまたぐ追跡につながりやすく、計測情報を広告に使わない、外部に提供しないという約束と衝突します。対局画面に広告を出さない方針もあります。
- **Checkout の戻り先で会員を有効にする。** 上の理由で採りません。
- **相関子に内部アカウント ID やメールアドレスを使う。** Stripe の記録から TetraBoard の利用者をたどれてしまいます。
- **ほかの決済代行（国内のものを含む）。** 今回は比較していません。収益化計画で Stripe と決めたうえで、その理由をこの ADR に残しています。

## 影響と未決

利用者への影響:

- サポーターになるには、Google か Discord との連携が必要です。決済の画面は Stripe のページに移り、メールアドレスとカード情報をそこで入力します。3D セキュアの認証を求められることがあります。
- サポーターにならない利用者には、取り扱う情報の変化はありません。計測の扱いも変わりません。
- 退会すると、課金も止まります。ただし、Stripe が自身の義務で保持する決済の記録まで TetraBoard から消せるとは説明しません。
- ポリシーの改定、規約、特定商取引法に基づく表示が公開の前に要ります（TB-191）。改定の内容によっては、既存の利用者に再同意を求めることになります。

引き継ぎ:

- **TB-191**: 利用規約、プライバシーポリシー、特定商取引法に基づく表示。決済の目的、Stripe の役割、Stripe が直接集める情報、TetraBoard が保持する情報、国外での取り扱い、解約と返金、退会時の課金の扱いを文言にします。
- **TB-193**: 実装とサンドボックスでの検証。課金状態の表、顧客ポータルの採否、支払い失敗の扱い、再送の期限を過ぎた後の復旧の経路、退会時の解約の方法、1 アカウント 1 契約を守る方式と重複した初回の決済の扱い、巻き戻りを防ぐ方式、現在の契約だけが会員の状態を更新すること、支払い済みの期限から特典の期限を出すこと、受け付けた照合の再試行か再実行の手段、D1 の復元後に未完了の Checkout Session も照合か失効させること、退会の直後の課金の停止を退会したアカウントについて試すこと（いまの退会の処理は未完了の退会をまとめて処理するので、滞留があると後回しになりうる）、D1 の復元で課金の対応を失わない手順、Webhook の署名検証と重複・順不同・並行・再加入後の旧契約の通知の試験。

**未確認**（後続で確かめ、確かめたら確認日と出典を添えて書き直します）:

- Billing の 0.7% がカードの 3.6% に重ねてかかるか（料金ページに合算の記載がない）。
- 3D セキュアが、この構成（Checkout のサブスクリプションのモードと、その後の継続の決済）で実際にどう動くか。公式の案内は 2025-06 のもので、その後の変更も確かめていません。サンドボックスとテスト用のカードで確かめます。
- Stripe の実際の設定（Checkout で集める項目、顧客ポータルの設定、Webhook のイベントの種類、Radar などの不正対策）。
- Stripe が集める端末・通信の情報の項目と、Stripe での保存期間。TetraBoard が保持する課金の情報の保存期間と、帳簿として残す必要の有無。
- Stripe への提供が個人情報保護法上の委託か第三者提供か、外国にある第三者への提供として何が要るか。
- 特定商取引法に基づく表示の内容と、「請求があれば遅滞なく開示」で足りるか。公開の可否と、特定商取引法・個人情報保護法への適合を、この ADR は判断しません。
- stripe-node の現在の版が Workers でそのまま動くか（`nodejs_compat` の要否、バンドルの大きさ）。
- pixivFANBOX の連携の手段。
